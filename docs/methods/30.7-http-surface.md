# Increment 30.7 — HTTP surface (user-authored REST request-tools)

> **Status:** planned. Spec source: `docs/design/app-surface-model.md` §2.2–2.3
> (the App Surface Model). This increment builds ONE new `Platform.kind: "http"`
> end-to-end — core schema + provider, source-runtime dispatch,
> platform-orchestration add, CLI setup, Web guided form. Independent of the
> Apps-page redesign (that's a parallel track); HTTP is a pure new surface the
> App layer later just displays.

---

## 0. TL;DR for the builder

Add an **`http` platform surface**: a REST API whose **tools the user authors by
hand** — the REST twin of the existing `cli` surface. Each request-tool declares
`{name, method, path, params[], description}` where every param has a **location**
(`path | query | header | body`). junction pre-builds one MCP tool per declared
request-tool and, on call, validates the agent's args → binds each to its location
→ makes the authed, timed, size-capped `fetch`.

**This reuses two proven, shipped machineries — do NOT invent new ones:**
- **Authoring model** = the `cli` surface (`CliConnectionSchema` / `createCliProvider`
  / `addCliPlatform` / the web guided-form): "operator declares tools[], one tool
  = one MCP tool, pre-built at construction."
- **Request-construction engine** = the `openapi` client (`packages/openapi-client/
  src/http.ts` `callOperation` + `tools.ts` `buildInputSchema` + the
  `OpenApiAuthSchema`): path/query/header/body binding, `validatePathValue`
  injection guard, `injectAuth` header injection, byte-cap + timeout + secret-free
  errors.

**HTTP = CLI's authoring skeleton + OpenAPI's request engine.** Almost nothing is
genuinely new; it's a recombination. The key inversion: CLI puts a param's
"location" in an argv *template segment*; HTTP puts `in: path|query|header|body`
**on the param itself** (exactly like OpenAPI).

**HARD CONSTRAINTS:** correctness/security over speed. Package boundaries: `core`
depends on nothing in-repo, no HTTP *server* in core (a `fetch` client is fine —
openapi-client already does it, but note it lives in `packages/openapi-client`, a
lib, NOT `core`; see §2 for where the provider lives). Web is server-only core
(secret handling stays server-side; the auth secret NEVER reaches the client
bundle or any tool output). `pnpm verify` is THE gate; run `pnpm dup` before
pushing near-dup UI (the web form mirrors the CLI form — dedup or keep honestly
separate). Must NOT regress any existing surface (mcp/openapi/graphql/cli).

### Where credentials fit (inc 28.9 — reuse, don't rebuild)
- HTTP is a **credentialed** surface. The credential kind matrix (inc 28.9) already
  supports `api-key`/`bearer`. The secret resolves to a plain `string | null`
  (like openapi/graphql) and injects via `injectAuth` into a header/query — NOT a
  `credentialEnvVar` like CLI. **verify-on-add:** wire HTTP into `verifyCredential`
  the way OpenAPI does — but OpenAPI is only verifiable via an operator-designated
  `verifyOperationId`; for HTTP, the analog is an **operator-designated verify tool**
  (a declared request-tool marked as the health check) OR honestly "not-verifiable"
  if none is designated. **Decide at build (see §4 open point); default to the
  OpenAPI precedent: verifiable only if the operator designates a safe GET tool.**

## 2. Where the code lives (package-boundary decision — READ FIRST)

**Question:** the `http` provider makes `fetch` calls. Does it go in `core` (like
`createCliProvider`) or in a lib (like `createOpenApiProvider` in
`packages/openapi-client`)?

**Decision: put the HTTP provider in its OWN lib `packages/http-client/`**, mirroring
`openapi-client`/`graphql-client`. Rationale:
- `core` has the `cli` provider, but CLI executes via the **sandbox** (a core
  concern) with no network. An HTTP `fetch` client is exactly the shape already
  factored OUT of core into `openapi-client`/`graphql-client` (the `core-not-http`
  depcruise rule bans core→undici/http). Adding a `fetch` provider to core would
  fight that boundary.
- `openapi-client` and `http-client` share the request-binding engine. **Extract the
  shared binding** (`buildRequest` from path/query/header/body params + `injectAuth`
  + the byte-cap/timeout `fetch` + secret-free errors) into a shared module both
  consume, OR have `http-client` depend on `openapi-client`'s exported helpers.
  **Recommend:** extract the pure binding engine into `openapi-client` exports (or a
  small shared `packages/http-runtime/`) and have both providers use it — rule of
  three is hit (openapi + http both bind params→request). **Decide the exact
  factoring at build; do NOT copy `http.ts` wholesale (jscpd will catch it, and
  it's the wrong-abstraction risk).**

So: **schema in `core`** (`HttpConnectionSchema` — pure types, like
`OpenApiConnectionSchema` lives in core), **provider in `packages/http-client/`**,
**dispatch in `source-runtime`**, **add-flow in `platform-orchestration` + cli +
web**.

**FACTORING DECISION (orchestrator, 2026-07-05 — resolved the §2 "decide at build"):**
depcruise allows lib→lib (a lib DAG; `libs-import-only-core` only bans lib→app).
So **`http-client` depends on `openapi-client`** and reuses its request-execution
engine. Concretely: **extract the shared "build + execute an HTTP request from a
resolved (baseUrl, method, pathTemplate, typed-params-with-location, auth, secret,
defaultHeaders, args, timeoutMs) → ToolResult" function out of
`openapi-client/src/http.ts` into an EXPORTED `buildAndExecuteRequest(...)`** (the
logic currently at http.ts ~L234-404: path binding + `validatePathValue` + query +
header + `injectAuth` + body + host-pinned `fetch` + byte-cap/timeout + secret-free
errors). openapi-client's `callOperation` keeps its schema-lookup half
(`findOperation` + `resolveBaseUrl` + extracting params from the raw spec op) and
then calls the shared `buildAndExecuteRequest`. http-client's `callTool` skips the
schema lookup (the tool IS the resolved operation) and calls the SAME
`buildAndExecuteRequest` with params taken from the `HttpRequestTool`. This is the
rule-of-three-honest dedup (2 consumers of one binding engine) with **no new
package** and **no behavior change to openapi** (pure extraction — its tests must
stay green, byte-identical behavior). Do NOT copy http.ts. If the extraction proves
awkward, a shared `packages/http-runtime/` lib is the fallback — flag it, don't
silently copy.

## 3. Build plan (suggested internal order — orchestrator QAs each real sub-step)

### Slice A — Core schema (`HttpConnectionSchema`) + PlatformKind. LAND FIRST.
`packages/core/src/schema/http-connection.ts` (new). Model on `CliConnectionSchema`
(tools[] authoring) + `OpenApiConnectionSchema` (connection fields) + reuse
`OpenApiAuthSchema` verbatim (import or re-export it — do NOT duplicate the auth
union). Shape:

```ts
// A declared param on a request-tool. Type set mirrors CliArgSchema; adds `in`.
HttpParamSchema = {
  name: /^[a-zA-Z][a-zA-Z0-9_]*$/,
  in: z.enum(["path", "query", "header", "body"]),   // ← the location (NEW vs cli)
  type: z.enum(["string", "number", "boolean", "enum"]),  // (path/body objects: see note)
  required: z.boolean().default(false),
  description: z.string().optional(),
  enum: z.array(z.string()).min(1).optional(),
  pattern: z.string().optional(),           // + the maxLength ReDoS-guard refine (copy from cli)
  maxLength: z.number().int().positive().max(4096).optional(),
}

HttpRequestToolSchema = {
  name: /^[a-zA-Z][a-zA-Z0-9_]*$/,          // becomes the MCP tool name (raw)
  description: z.string(),                    // REQUIRED (it's the knowledge) — NOT optional
  method: z.enum(["GET","POST","PUT","PATCH","DELETE","HEAD"]),
  path: z.string(),                          // e.g. "/repos/{owner}/{repo}/issues" — {placeholders}
  params: z.array(HttpParamSchema).default([]),
  // OPTIONAL rich fields:
  responseHint: z.string().optional(),
  timeoutMs: z.number().int().positive().max(120_000).optional(),
  confirm: z.boolean().optional(),           // confirm-before-call hint (surfaced later; store now)
}
// Refine: every {placeholder} in `path` MUST have a declared param with in:"path"
//         AND every in:"path" param MUST appear as a {placeholder} (mirror cli's
//         argv↔args cross-check L160-175). At most ONE in:"body" param (the JSON body).

HttpConnectionSchema = {
  baseUrl: z.string().url(),                 // https/http; host-pinned at call time
  auth: OpenApiAuthSchema.optional(),        // REUSE — apiKey|bearer|basic|oauth2
  defaultHeaders: z.record(z.string()).optional(),
  tools: z.array(HttpRequestToolSchema).min(1),
}
```
- `packages/core/src/schema/platform.ts`: add `"http"` to `PlatformKind` (L17) +
  `http: HttpConnectionSchema.optional()` (L56) + import.
- Export from `packages/core/src/schema/index.ts` + `core/src/index.ts`.
- **Note on body:** v1 body = a single `in:"body"` param whose value is passed
  through as the JSON body (like OpenAPI's `body` key). A typed body object schema
  is a future refinement — keep v1 to "one body param, JSON-stringified".
- **Tests:** schema round-trips; the path↔param cross-check rejects a `{placeholder}`
  with no `path` param and a `path` param with no placeholder; ≤1 body; auth union
  parses; enum/pattern refines fire.

### Slice B — Provider (`createHttpProvider`) in `packages/http-client/`. Needs A.
- New lib `packages/http-client/` (mirror `graphql-client`'s package.json/tsdown/
  exports skeleton). Depcruise: it may import `core` (types) + the shared binding
  engine; nothing imports it except source-runtime.
- **Extract/share the request engine** (see §2): `buildInputSchema` (params→flat
  JSON Schema, generalize `openapi-client/tools.ts:114-160` to take the http params)
  + `buildAndFetch` (path/query/header/body binding + `validatePathValue` +
  `injectAuth` + byte-cap + timeout + secret-free errors from
  `openapi-client/http.ts`). Prefer factoring these out of openapi-client so both
  share ONE copy.
- `createHttpProvider(connection: HttpConnection, secret: string | null)`:
  - `listTools()` → pre-build one `ProviderTool` per `connection.tools[i]` (name,
    description, `buildInputSchema(tool.params)`) — exactly `createCliProvider`'s
    pre-build shape.
  - `callTool(rawName, args)` → resolve tool by name (`tool-not-found`) → validate
    args against the tool's params (types/enum/pattern/maxLength/required/
    unknown-keys) → bind each param by its `in` to path/query/header/body → build
    the request against `connection.baseUrl` + `defaultHeaders` → `injectAuth(secret)`
    → `fetch` with the tool's `timeoutMs ?? default` + byte cap → `ToolResult`
    (`isError: status >= 400`).
  - `close()` no-op.
- **Security (mirror openapi exactly):** host-pinned base URL (agent args never set
  host); `validatePathValue` rejects `/`,`..`,control chars,URL schemes in path
  params; secret only ever in the request (never in output/errors/logs);
  `redirect:"manual"`; error mapping via `constructor.name`.
- **Tests (against a local mock server / undici MockAgent):** a GET tool binds a
  path param + query; a POST tool binds a JSON body; auth header injected (assert on
  the outgoing request, secret present in request, ABSENT from the returned
  `ToolResult`); path-injection (`../`) rejected; 4xx → `isError:true`; oversize
  response capped; timeout → clean error.

## 4. Open design points (resolve at build; surface only if outcome-changing)

- **verify-on-add for http:** recommend the OpenAPI precedent — verifiable ONLY via
  an operator-designated safe GET request-tool (a `verifyToolName?` on the
  connection), else honestly "not-verifiable". Do NOT auto-fire an arbitrary
  declared tool (could be a POST/DELETE). Hold loosely; the invariant is *never fire
  a mutating request the operator didn't designate*.
- **Raw escape-hatch tool:** the design (`app-surface-model.md` §2.3) allows an
  OPTIONAL raw `request(method, path, body)` tool. **v1: OMIT it** (defined typed
  tools only — simpler, safer, and the norm). Record as a future (§6) with the
  trigger "an app needs arbitrary calls beyond declared tools."
- **Body typing:** v1 = one `in:"body"` param, JSON pass-through. Typed body schema
  deferred.
- **Auth reuse across surfaces:** out of scope (one credential → one platform holds;
  that's a separate deferred item in the design doc §9).
