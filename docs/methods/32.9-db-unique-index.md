# 32.9 — credentials `(platform_id, profile_name)` unique index (dedup-then-constrain)

Inc 30.12 closed the duplicate-account hole at the app layer only (`addCredential` guard). This adds the DB-level constraint: migration 0010 dedups any legacy duplicate rows, then creates the unique index. Belt-and-suspenders; the app guard stays.

**Proof-of-done:**
1. Migration 0010: `DELETE` all but the NEWEST row per `(platform_id, profile_name)` group (ULID ids sort by time → `MAX(id)`), then `CREATE UNIQUE INDEX credentials_platform_profile_unique ON credentials (platform_id, profile_name)`.
2. A raw INSERT violating the index fails with SQLITE_CONSTRAINT; via the app path, a violation that slips past the 30.12 guard surfaces as the typed `duplicate-account` CredentialError (remapped at the add-credential create call site), and the just-set store secret is still cleaned up.
3. Migration test proves the dedup on a PRE-index schema seeded with real duplicates (stage rows on 0000..0009, then apply 0010) — survivors correct, other data intact, dup INSERT rejected.
4. `pnpm verify` green; `pnpm drizzle-kit generate` used for the snapshot/journal (never hand-authored meta).

## Changes
1. **schema.ts**: add the composite `uniqueIndex("credentials_platform_profile_unique").on(t.platformId, t.profileName)` to the credentials table, mirroring the existing pattern.
2. **Generate migration 0010** with `pnpm drizzle-kit generate` **from the repo ROOT** (drizzle.config.ts lives at root; correct snapshot + journal `when` = real current time — do NOT touch the 0003 journal entry; that known non-monotonic `when` bug is a SEPARATE deliberately-unfixed item). Then hand-edit ONLY the generated `.sql`: TWO hand statements ABOVE the CREATE UNIQUE INDEX, each in its own `--> statement-breakpoint` chunk, in this order:
   **(2a) Repoint source_refs off loser rows FIRST — without this the migration BRICKS real DBs.** `source_refs.credential_id → credentials.id` is ON DELETE **RESTRICT** (schema.ts:62-64, live since 0004) and `pragma foreign_keys = ON` is set BEFORE `migrate()` (db/index.ts:28-32); the drizzle migrator wraps ALL pending migrations in ONE transaction, so a FK failure rolls back and every subsequent boot fails with migration-failed. (`PRAGMA foreign_keys=OFF` is a no-op inside a transaction; `defer_foreign_keys` still fails at COMMIT — do not attempt either.)
   ```sql
   UPDATE source_refs SET credential_id = (
     SELECT MAX(c2.id) FROM credentials c2, credentials c
     WHERE c.id = source_refs.credential_id
       AND c2.platform_id = c.platform_id AND c2.profile_name = c.profile_name
   )
   WHERE credential_id IS NOT NULL
     AND credential_id NOT IN (SELECT MAX(id) FROM credentials GROUP BY platform_id, profile_name);
   ```
   (Consistent with keep-newest: the route follows the surviving credential. Cannot violate source_refs' own unique index — that's (profile_id, tool_namespace). Nothing else references credentials.id — verified across schema + all migrations.)
   **(2b) The dedup DELETE:**
   `DELETE FROM credentials WHERE id NOT IN (SELECT MAX(id) FROM credentials GROUP BY platform_id, profile_name);`
   (SQL-ONLY dedup — never via removeCredential/app code. Keep-newest: latest connect wins. Losers' store secretRefs are consciously orphaned — harmless dangling handles, covered by the 32.7 orphan-observability class. ULID note: ids are bare 26-char Crockford-base32 ULIDs, TEXT/BINARY collation → lexicographic MAX == newest; the only tie-break gap is two adds in the same millisecond picking a random winner — negligible, note it.)
   **Comment-placement trap:** the real migrator runs each breakpoint chunk via better-sqlite3 `prepare()`, which THROWS on a comment-only chunk ("contains no statements") — while the TEST helper uses `exec()` which tolerates them, so a mis-placed comment is green-in-test, crash-in-prod. All `--` comment lines MUST live in the same chunk as (i.e. directly above) their statement, never as their own breakpoint segment.
   **Atomicity (so you don't add defensive scaffolding):** the migrator runs one transaction around the whole pending set — UPDATE+DELETE+CREATE INDEX are atomic together; partial application on crash is impossible.
3. **add-credential.ts** — pin the remap INSIDE writeCredential's EXISTING `orElse` (line ~176), i.e. after the `store.delete(...)` cleanup completes: branch on `dbErr.kind === "constraint-violation"` → `errAsync({ kind: "duplicate-account", platformId: credential.platformId, account: credential.profileName })`, else `errAsync(dbErr)`. Cleanup-before-remap is then structural — do NOT append a second `.orElse` and do NOT change the shared generic `mapDbError`. Add a short comment accepting the theoretical PK-collision false-positive (a fresh-ULID PK collision also maps to SQLITE_CONSTRAINT; negligible — FK failures are separately mapped to "in-use" so they're unaffected).
