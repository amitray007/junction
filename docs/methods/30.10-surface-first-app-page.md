# Increment 30.10 — Surface-first `/app/:id` page (read-only)

> **Status:** planned (method file drafted 2026-07-06; awaiting doc-review + approval).
> Spec source: `docs/design/app-surface-model.md` §7 (UX shape) + §4.6/§4.7 +
> `docs/design/app-surface-model-roadmap.md` inc 30.10.
>
> **The user-visible payoff of the App Surface Model track.** Rebuild `/app/:id`
> from a flat connections list into a **surface-first capability view**: for each
> of the app's surfaces (MCP/OpenAPI/GraphQL/HTTP/CLI), show whether it's connected,
> what tools it exposes, and its catalog details. **Read/display only — NO connect
> writing** (that's 30.11). Renders the inc-30.8 catalog + the inc-28 probe.

---

## 0. TL;DR for the builder

Today `/app/:id` (`packages/web/src/routes/app.$id.tsx`) shows a flat list of the
user's **connections** to an app (account + kind + status + a lifecycle ⋯ menu).
Rebuild it **surface-first**: the catalog defines an app's surfaces; show each one,
mark connected-vs-available, and (for a connected surface) list its **actual tools**
via the inc-28 probe. All surfaces shown **equally**; a surface with no tools shows
**"no tools available"** honestly (per §4.7).

Three load-bearing changes (research-confirmed 2026-07-06):
1. **Expose the RICH catalog to web.** `readApps()` (`data.server.ts:470`) currently
   returns `catalog: listApps()` — the surfaces-BLIND legacy `AppDefinition`.
   Switch the per-app path to `getCatalogEntry(id)`/`listCatalogEntries()` so
   `surfaces[]` reach the page. Extend the `AppMeta` DTO (currently `= AppDefinition`,
   `data.server.ts:385`) to carry `surfaces` (metadata-only — NO secrets).
2. **A pure surface↔connection intersection helper** (NEW, in `core/apps/`, NOT
   inside surfaces-blind `group.ts`): given an app's catalog `surfaces[].kind` +
   the app's live `AppGroup.connections[].kind`, compute per-surface
   `{available, connected, connections[]}`. Pure, testable, no I/O.
3. **Extend the probe to be app/platform-scoped + surface an inputSchema summary.**
   `probeSource` (`probe.server.ts:94`) is PROFILE-scoped (`{profileId, namespace}`)
   and `ProbeToolEntry` (`probe.server.ts:88` = `{namespaced, raw, description?}`)
   drops `inputSchema`. The page needs to list a surface's tools without a profile.
   Add an app/platform-scoped probe entry point + an optional param-summary.

**HARD CONSTRAINTS:** web is **server-only core** — all core/secret access stays in
`*.server.ts`/`createServerFn` handlers; the page is **metadata-only at the edge**
(no secretRef, no token — mirror `readApps`' existing discipline). Design-token
discipline (`docs/rules/web.md`): use the CSS tokens + existing UI primitives, no
ad-hoc colors. `pnpm verify` is THE gate; **web work also needs `pnpm dup` before
push** (jscpd bit inc 30). **QA is agent-browser against the REAL running server**
(§6) — a green build is NOT proof a web page works (the "green but blind" class).

- Loader (`:94`) calls `getApps()` (`data.functions.ts`), gets `AppsData`, calls
  `loadAppDetail(id, data)` → `{ app: AppDisplay, connections: ConnectionMeta[] }`.

### The web app-data path — `packages/web/src/server/data.server.ts`
- **`readApps(): Promise<AppsData>`** (`:414`, returns at `:470`
  `{ catalog: listApps(), groups: groupMetas }`) — **`listApps()` is surfaces-BLIND**
  (the legacy `AppDefinition[]`). ⚠️ *(Note: grep this file with `grep -a` — it has a

- `AppMeta = AppDefinition` (`:385`). `ConnectionMeta` (`:387`) = `{credentialId?,
  account, platformId, platformDisplayName, kind, lastVerifiedAt?, lastVerifyResult?,

  groups: AppGroupMeta[]}`.
- Uses core's pure **`groupByApp`** (`:435`) — identity-based, surfaces-blind.
  `readApps` is the ONLY web file importing `@junction/core` (boundary held).

### The merged 30.8 catalog — schema in `catalog-schema.ts`, ACCESSORS in `catalog/index.ts`
- **`getCatalogEntry(id)` / `listCatalogEntries()` live in `packages/core/src/apps/catalog/index.ts`**
  (`:31`/`:36`), re-exported from `@junction/core` (`index.ts:61`) — NOT in
  `catalog-schema.ts` (that's schema-only). Import from the `@junction/core` barrel. They
  return the RICH `AppCatalogEntry`
  (`{id, displayName, supportedKinds, auth, aliases?, setupHints?, iconSlug?,
  surfaces?: AppSurface[], help?: AppHelp}`). `AppSurface` = `{kind, displayName,
  connection, auth, build, verify?, docs?, agentGuidance?, starterTools?, notes?}`.
- `getApp`/`listApps` still return the surfaces-STRIPPED `AppDefinition` (back-compat).
- **GitHub has 5 authored surfaces** (openapi/graphql/mcp/cli/http, http empty) — the
  ideal QA fixture. Most other apps are thin (no surfaces) — the page must handle both.

### The inc-28 probe — `packages/web/src/server/probe.server.ts`
- `probeSource({profileId, namespace})` (`:94`) → `{ok, namespace, tools:
  ProbeToolEntry[]} | {ok:false,…}`. `ProbeToolEntry` (`:88`) = `{namespaced, raw,

## 2. What the page becomes (UX — §7 of the design)

`/app/github` (and every app), top → bottom:

1. **Header** — `PageHeader` with the `BrandIcon` + app name + a subtitle
   "N surfaces · M connected" where **N = catalog surfaces, M = surfaces with ≥1
   connection** (surface-count, NOT connection-count — decided, doc-review M4).
2. **Surfaces** — the centerpiece. For EACH catalog surface (`getCatalogEntry(id).surfaces`),
   a **surface card**:
   - Kind tag + `displayName` + a **state** (crisp definitions — doc-review I1, §2a below).
   - The **auth** it uses (a chip — "via OAuth · github" / "token") — metadata only.
   - **Tools panel** — THREE distinct renderings (doc-review I2), never conflated:
     (a) **tools list** (probe ok, ≥1) — name + description + the `params` summary;
     (b) **"No tools available"** (probe ok, empty — the honest-empty case, e.g.
     GitHub's http surface, using its `notes[]`/`agentGuidance`);
     (c) **"Couldn't list tools — <reason>"** (probe ERRORED — network/credential/
     upstream) — semantically OPPOSITE to (b); must render differently.
   - Catalog **details**: `docs` link, `help.install`/`authSetup` hints, `agentGuidance`.
   - Connection rows for THIS surface grouped under it (§2b). **All surfaces equal** (§4.7).
3. **"Other connections" bucket** (doc-review C2 — load-bearing) — any live connection
   whose `kind` matches NO catalog surface (an uncatalogued/manually-added platform, or
   an app-level mismatch) renders in a terminal **"Other connections"** group, NEVER
   dropped. Also the home for the `id === "other"` synthetic app (doc-review I4).
4. **Empty/thin app** (no `surfaces`, OR `getCatalogEntry` undefined incl. `"other"`) —
   fall back to today's `EmptyAppState` + flat connections list; surface-first is
   additive, never worse than today.

### 2a. Surface-state truth table (doc-review I1 — compute consistently)
State = f(has-catalog-surface, has-≥1-connection, any-connection-healthy, probe-tools):
- **not-in-catalog** → the connection lands in "Other connections" (§2 item 3), no card.
- **available** — catalog surface, **0 connections** ("junction can stand this up").
- **connected** — ≥1 connection, but no healthy one yet (all `auth-failed`/`configured`)
  OR probe not yet run.
- **serving** — ≥1 **healthy** connection AND the probe returned ≥1 tool.
- (probe error is a TOOLS-PANEL state (§2 item 2c), NOT a surface state — a surface can
  be `connected` with a failing probe.)
Reconcile with the per-connection `connectionStatus()` (`app.$id.tsx:110`,
connected/expiring/auth-failed/configured/no-auth) — surface state is the AGGREGATE
("any healthy"); the individual connection rows keep their own `StatusBadge`. (Design
§7's serving/paused/not-set-up names map to serving/available/not-in-catalog here — use
THESE names; note the reconciliation in a comment.)

### 2b. Connections per surface — the multi-account wedge (doc-review C1/C4)
A surface can have **multiple account-connections** (two GitHub accounts on the mcp
surface). Render the existing `ConnectionRow` (account + status + ⋯ lifecycle menu,
`connection-dialogs.tsx` verbatim — no lifecycle changes) for EACH connection, grouped
under its surface. **Tools are probed PER CONNECTION** (a `(platform, credential)`
pair — different accounts can have different toolFilters/tools), shown under that
account's row (or a surface-level list when there's exactly one connection). Do NOT
probe once per surface and pretend all accounts share it.

**Explicitly NOT in this increment:** any "Connect"/"Add surface" button that WRITES
(30.11); the multi-surface-per-kind model (30.12); catalog auto-fill.

## 3. The three build changes (detail)

### 3a. Rich catalog to the web edge (`data.server.ts` + `data.functions.ts` types)
- Add a per-app rich path: either extend `readApps()` to also attach each catalog
  app's `surfaces`. **DECIDED (doc-review I3): add a NEW `readAppDetail(id)` server-fn**
  (surfaced as `getAppDetail(id)` in `data.functions.ts`) returning
  `{app: {id, displayName, iconSlug?, help?}, surfaces: SurfaceView[],
  otherConnections: ConnectionMeta[]}`. Keep `readApps()`/`getApps()` for the INDEX
  unchanged (it only needs the light `listApps()` spine — don't bloat it).
  - **Loader change (`app.$id.tsx:94`):** the loader now calls `getAppDetail(id)`
    (not `getApps()` + `loadAppDetail`). Retire `loadAppDetail`/`AppDisplay`; keep an
    `OTHER_APP_DISPLAY`-style thin path for `id==="other"` / undefined-catalog (§2 item 4).
  - **`getCatalogEntry`/`listCatalogEntries` live in `packages/core/src/apps/catalog/index.ts`**
    (NOT `catalog-schema.ts` — doc-review corrected the §1 attribution), re-exported from
    `@junction/core` (import from the barrel).
- **`SurfaceView` DTO (metadata-only, a FRESH plain type — NOT a re-export of core's
  `AppSurface`, which carries `connection`/`build` secrets):** `{kind: string,
  displayName, auth: AppAuth[], docs?, agentGuidance?, notes?, state:
  "available"|"connected"|"serving", connections: SurfaceConnection[]}` where
  `SurfaceConnection = ConnectionMeta & { tools: ToolListResult }` and
  `ToolListResult = {status:"ok"; tools: ProbeToolEntry[]} | {status:"error"; reason: string}`
  (the three tools-panel states, §2 item 2). **NEVER** include `build`/`connection`/
  secretRef/token/raw-inputSchema. Dropped `hasStarterTools` (doc-review M1 — a 30.11
  connect-time concept, not read-only display).
- Boundary: all in `*.server.ts`; the route imports only the server-fn + re-exported
  TYPES (mirror `data.functions.ts:22-36`). Each handler calls `assertLocalHost()`.

### 3b. Pure surface↔connection intersection (NEW core helper)
- New pure fn in `core/apps/surface-connections.ts` (NOT in `group.ts`), **generic
  over the connection element so it carries FULL connections through** (doc-review C1):
  ```ts
  intersectSurfaces<C extends { kind: string }>(
    surfaces: { kind: string }[],
    connections: C[],
  ): { matched: { kind: string; connections: C[] }[]; leftover: C[] }
  ```
  — for each catalog surface, `connections` = the subset of the app's connections whose
  `kind` matches; **`leftover`** = connections whose kind matches NO surface (doc-review
  C2 — the "Other connections" bucket; NEVER dropped). Pure, no I/O, unit-tested.
  Do NOT return bare `connectionKinds` (the page needs full `ConnectionMeta` to render
  `ConnectionRow`).
- **⚠️ OPEN DECISION — same-kind ambiguity (feasibility CONFIRMED safe for 30.10).**
  Matching is **by `kind`**. If an app had TWO surfaces of the same kind, kind-matching
  is ambiguous — BUT no current catalog entry has a same-kind collision (GitHub's 5
  surfaces are 5 distinct kinds — the QA fixture has zero ambiguity). **Assume one
  surface per kind for 30.10, match by kind, `// LIMITATION`-comment it**; the
  multi-surface-per-kind model is 30.12. *(This is DISTINCT from the multi-ACCOUNT wedge
  in §2b — multiple accounts on ONE surface IS in scope and must render.)*

### 3c. Platform-scoped probe + inputSchema summary (`probe.server.ts`)
- The page shows a connected surface's tools **PER CONNECTION** (§2b). Add
  `probeSurface({platformId, credentialId?})` → `ToolListResult`. **DECIDED path
  (feasibility-confirmed): build the provider via `buildProvider(platform, secret,
  paths).listTools()` DIRECTLY — NOT `createProfileProxy`/`makeResolveProvider`.**
  - **Why not the profile proxy:** `makeResolveProvider` (`resolve-provider.ts:84`)
    HARD-RESTRICTS to `mcp`/`openapi` and skips graphql/http/cli — using it would make
    3 of 5 surfaces silently return nothing. `buildProvider` handles all 5 kinds.
  - **Exact precedent to mirror: `packages/cli/src/commands/debug.ts:95-160`** —
    `resolveCredentialSecret(repos, paths, credential)` → `toResolvedSecret(secret,
    kind)` → `buildProvider(platform, …, paths)` → `provider.listTools()` →
    **`provider.close()` in a `finally`** (the inc-11 connection-leak/hang gotcha —
    MANDATORY).
  - **Two graceful arms (feasibility):** `resolveCredentialSecret` returns
    `ok({secret: null})` for a lost/cleared secret AND `err({kind:"credential"})` when
    the store fails to open — map BOTH to `ToolListResult.error` (an honest "couldn't
    list"), never throw. A no-credential connection → also `error`/"not connected".
  - Returns **raw, un-namespaced** tool names (no profile namespace here) — so
    `ProbeToolEntry.namespaced` is absent/equals `raw` on this path (that's correct
    for a per-surface list; differs from the profile probe's namespaced output).
- **Extend `ProbeToolEntry`** with an optional `params?: string` — derived server-side
  from `ProviderTool.inputSchema` (`core/sources/provider.ts:18` — present at the
  `listTools()` layer). **Format rule (doc-review M2):** JSON-Schema `required[]` first
  then optional, comma-joined, `*` suffix = required, cap at ~8 params with `…` overflow,
  object/array params by name only. Additive/optional — the inc-28 profile probe is
  unchanged.
- **SECURITY:** the secret is used server-side only; `ProviderTool` has no secret field,
  the DTO returns names/descriptions/param-summary only — the secret NEVER crosses the
  transport boundary (the §6 adversarial sweep proves it, positive-controlled: a real
  tool list MUST come back through the credentialed path so the sweep tested a LIVE path).
- **Unknown surface kind** (doc-review I5): the card renders a generic tag (the raw kind
  string) + default glyph, never a crash (`kind` is `string` at the edge; `grpc` is a
  future candidate).

## 4. Boundary & security (web is server-only core)

- All core/credential access is inside `data.server.ts`/`probe.server.ts`
  (server-only); route components import only server-fns + re-exported TYPES.
- **Metadata-only at the edge:** `SurfaceView`/`ConnectionMeta`/`ProbeToolEntry`
  carry NO secretRef, token, client_secret, or raw inputSchema. The probe's tool
  listing uses a credential server-side but returns only names/descriptions/param-summary.
- **The adversarial sweep (§6) is mandatory** — a seeded secret must be absent from
  the DOM, HAR (all response bodies), SSR HTML, and the web log, with the credentialed
  probe path genuinely exercised (a real tool list returned through it).
- `junction-web-verify`'s leak-check + `web:smoke` gates must pass.
