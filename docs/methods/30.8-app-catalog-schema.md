> **Status:** planned (method file drafted 2026-07-06; awaiting user approval —
> per-increment loop step 4). Spec source: `docs/design/app-surface-model.md`
> §4.6/§4.7 + `docs/design/app-surface-model-roadmap.md` inc 30.8.
>
> **This increment defines the catalog SCHEMA and proves it by hand-authoring
> GitHub through it.** It is PURE `core` data + Zod — **no web, no importer, no
> connect wiring** (those are 30.9/30.10/30.11). The point is to nail the format
> against real code before anything depends on it.

## 0. TL;DR for the builder

Turn junction's inc-30 App catalog (today a **489-line `catalog.ts`** — a
TypeScript array of **45** `AppDefinition`s, **43** with `iconSlug`) into a
**loaded, Zod-validated, richer catalog** that also carries **per-surface setup
data** — the base the App page + one-click connect (later increments) build on.

> **Count discipline (a doc-review caught a wrong literal):** "45" is the current
> `APPS` length — but do NOT hardcode it as a test oracle. The migration's
> correctness test must **diff the new catalog's ids/fields against the OLD `APPS`
> array**, computed from source, so it can never silently pad or drop an entry.

Concretely:
1. **Extend the catalog schema** — a NEW `AppCatalogEntrySchema` (Zod) that is a
   superset of today's `AppDefinition`, adding a `surfaces[]` array (per-surface
   connection templates + auth + build recipe + verify), plus app-level `help`
   (install/docs/agentGuidance) and optional per-surface `starterTools`.
2. **Ship it as JSON files, folder-per-app** — `packages/core/src/apps/catalog/<id>/catalog.json` (+ `help.json`, + `tools/http.tools.json` where used),
   loaded + validated at read. Migrate the 45 existing apps.
3. **Hand-author GitHub fully** — all real surfaces, as the forcing-function proof
   the schema actually expresses a real app. **HTTP ships EMPTY for GitHub** (the
   gap-filler rule — OpenAPI covers REST).
4. **Preserve inc-30 back-compat** — `groupByApp`/`appIdForConnection`/`listApps`
   still work byte-identically (the reverse-coverage regression guard from inc-30
   stays green; every non-generic OAuth provider still has an app).

**HARD CONSTRAINTS:** `core` stays pure — **no HTTP, no I/O to the network, and NO
`fs.*Sync` / `readFileSync` in `packages/core/src`** (the boundary-guard hook,
`.claude/hooks/boundary-guard.mjs:58-60`, HARD-BLOCKS the edit — a feasibility
review confirmed `readFileSync` at init is not writable to a core src file). So
the catalog is **compiled to a `.ts` module of validated data at build time** (see
§2a — DECIDED codegen, no runtime `fs`), NOT read from disk at init. No web types
leak into core. `pnpm verify` is THE gate. This is **data + schema only** — if you
find yourself editing the connect flow or the web layer, STOP: that's 30.10/30.11.

## 1. Ground truth (verified 2026-07-06 — the schemas the templates must match)

The catalog's per-surface **connection templates** must produce valid instances of
these SHIPPED schemas. Field-exact (file:line):

### 1a. `PlatformSchema` — `packages/core/src/schema/platform.ts:25`
- `PlatformKind` enum (`platform.ts:18`): `["mcp","openapi","graphql","cli","http","custom"]`.
- Fields: `id` (branded `PlatformId`), `kind`, `displayName`, `specUrl?`, `baseUrl?`,
  and the per-kind connection as **flat optional fields**:
  `connection?` (MCP — **note: named `connection`, NOT `mcp`**), `openapi?`,
  `graphql?`, `cli?`, `http?`.
- **NO `superRefine`** — the schema does NOT force "kind X ⇒ field X"; the
  `addXPlatform` orchestration fns set `kind`+field together. **The catalog
  templates follow the same convention.** `"custom"` has no connection field.

### 1b. Per-surface connection schemas (what a template must fill)
- **MCP** `McpConnectionSchema` (`mcp-connection.ts:61`), discriminated on `transport`:
  - `http`: `{ transport:"http", url:string.url, auth?: McpHttpAuth }`.
    `McpHttpAuth` = `{scheme:"bearer", header?=default "Authorization"}` OR
    `{scheme:"header", name:string}`.
  - `stdio`: `{ transport:"stdio", command:string, args?=[], tokenEnvVar?, env? }`
    (env has a denylist refine — LD_*/DYLD_*/NODE_OPTIONS/master-key keys rejected).
- **OpenAPI** `OpenApiConnectionSchema` (`openapi-connection.ts:90`):
  `{ spec: SpecSource, baseUrl?, auth?: OpenApiAuth, defaultHeaders?, maxTools?,
     select?, verifyOperationId? }`. `SpecSource` = `{from:"url",url}` |
  `{from:"file",path}` | `{from:"inline",document}`.
- **GraphQL** `GraphQlConnectionSchema` (`graphql-connection.ts:28`):
  `{ endpoint:string.url, auth?: OpenApiAuth, defaultHeaders?, schemaSdl?, maxQueryBytes? }`.
- **HTTP** `HttpConnectionSchema` (`http-connection.ts:263`):
  `{ baseUrl:string.url(^https?://), auth?: OpenApiAuth, defaultHeaders?,
     tools: HttpRequestTool[].min(1) }`. `HttpRequestTool` (`:149`) =
  `{ name(/^[a-zA-Z][a-zA-Z0-9_]*$/), description(min1), method(GET|POST|PUT|PATCH|DELETE|HEAD),
     path, params?=[], responseHint?, timeoutMs?(≤120k), confirm? }`; `HttpParam` (`:49`)
  = `{ name, in(path|query|header|body), type(string|number|boolean|enum), required?=false,
     description?, enum?, pattern?, maxLength?(≤4096) }` (8 tool-refines + 4 param-refines —
  see the extraction; the catalog's `starterTools` MUST satisfy them).
- **CLI** `CliConnectionSchema` (`cli-connection.ts:196`):
  `{ tools: CliTool[].min1, credentialEnvVar? }`. `CliTool` = `{name, description?,
     argv: CliArgvSegment[].min1, args?=[], policy: CliPolicy }` (argv[0] must be an
  absolute-path literal; policy carries cwd/readPaths/writePaths/allowNet/timeoutMs).

### 1c. Shared auth — `OpenApiAuthSchema` (`openapi-connection.ts:51`, reused by openapi/graphql/http)
Discriminated on `scheme`: `apiKey{in:header|query|cookie, name}` | `bearer{header?=Authorization}`
| `basic{username}` | `oauth2{}`.

### 1d. `AddXPlatformInput` — `packages/platform-orchestration/src/` (the build recipe's TARGET)
- **Two mapping styles (load-bearing):**
  - **Flattened** — MCP/OpenAPI/GraphQL take structured fields:
    `AddMcpPlatformInput{id,displayName,transport,url?/command?,authHeader?,tokenEnvVar?,env?,args?}`
    (`mcp.ts:9`); `AddOpenApiPlatformInput{id,displayName,specUrl,baseUrl?,auth?:AuthInput,maxTools?,select?,verifyOperationId?}`
    (`openapi.ts:29`); `AddGraphQlPlatformInput{id,displayName,endpoint,auth?:AuthInput,defaultHeaders?}` (`graphql.ts:19`).
  - **Opaque descriptor** — HTTP/CLI take `{id,displayName,descriptor:unknown}` (the
    full `HttpConnection`/`CliConnection` object, JSON-parsed then schema-validated)
    (`http.ts:12`, `cli.ts:11`).
- **`AuthInput`** (`auth.ts:11`, shared openapi+graphql): `{scheme?:apiKey|bearer|basic, in?, name?, username?}`.
  ⚠️ **`oauth2` is NOT a settable `AuthInput.scheme`** — it's only *derived from a spec*
  (`deriveAuthFromSpec`). See §5 "Known gap".

### 1e. Current catalog (what we migrate) — `packages/core/src/apps/catalog.ts`
- Plain TS: `AppAuth` union (`:27`) `{oauth2,providerId}|{token}|{byo}|{none}`;
  `AppDefinition` interface (`:33`) `{id,displayName,supportedKinds:PlatformKind[],
  auth:AppAuth[],aliases?,setupHints?,iconSlug?}`; `APPS` array (`:77`, **45 entries**);
  `getApp` (`:482`), `listApps` (`:487`). Consumed by `group.ts appIdForConnection`
  (exact id/alias/displayName + `oauthMeta.providerId`) — **must keep working**.
- `Credential` build target — `CredentialKind` `["api-key","bearer","oauth2","file","env"]`
  (`credential.ts:14`); `oauthMeta` refs (`providerId`, `clientIdRef`, …).

## 2. The schema to build (DECIDED — JSON, folder-per-app, extends AppDefinition)

### 2a. Files & loading
```text
packages/core/src/apps/catalog/
  github/
    catalog.json           # core: identity + surfaces[] + build + verify
    help.json              # rich: install, docs, agentGuidance (may be absent)
    tools/                 # optional; only for user-authored surfaces
      http.tools.json      # (github: ABSENT — HTTP is empty, gap-filler rule)
  <id>/ …                  # all 45 apps migrated (authored .json source)
  index.ts                 # imports catalog.generated.ts, exports listApps/getApp
  catalog.generated.ts     # COMMITTED, generated — the data that actually ships
```
- **Loading — DECIDED: build-time codegen, NO runtime `fs`** (two reviews converged
  here; `readFileSync` in core is hard-blocked by the boundary-guard hook, and the
  `db/migrations` "asset-copy" pattern is NOT a precedent — migrations are read by
  drizzle's own `migrate()`, not by core code). So:
  - The **authored source** is the per-app `catalog.json`/`help.json`/`tools/*.json`
    (human- + importer-writable).
  - A **generator script** — `packages/core/scripts/gen-catalog.mjs` (a `.mjs`
    **OUTSIDE `packages/core/src`** so the boundary guard doesn't block its `fs`
    reads) — reads all the `.json`, `JSON.parse` → `AppCatalogEntrySchema.parse`
    (**fail loud** on a malformed/absent-required entry — a bad catalog file is a
    build-time error, non-zero exit, never a silent skip), and emits a **committed
    `catalog.generated.ts`**: a plain TS module of validated object literals.
  - `index.ts` imports `catalog.generated.ts` (pure in-memory data, zero `fs`) and
    re-`AppCatalogEntrySchema.parse`s at module load as a belt-and-suspenders check.
  - **This is exactly the `brand-icons.generated.tsx` pattern (inc-30.5)** — authored
    data → generator script → committed generated TS, run manually via a `package.json`
    script (`gen:catalog`), NOT wired into the bundler. tsdown bundles the generated
    `.ts` into `dist/index.js` automatically (no `cpSync`, simpler than migrations).
    Note: `brand-icons` lives in `packages/web` (web may touch `fs`); ours is the
    same *shape* but the script sits in `packages/core/scripts/` (a dev/build script,
    not `src/`).

### 2b. `AppCatalogEntrySchema` (Zod — the new schema; superset of AppDefinition)
Author in `packages/core/src/apps/catalog-schema.ts`. Shape:

```ts
// Backwards-compatible core (every existing AppDefinition field):
id, displayName, supportedKinds: PlatformKind[], auth: AppAuth[],
aliases?, setupHints?, iconSlug?,

// NEW — the surface dimension:
surfaces?: AppSurface[]        // optional so a thin/legacy entry still validates

// NEW — app-level rich help (may live in help.json, merged on load):
help?: {
  category?: string[]; homepage?: string; statusPage?: string;
  description?: string; agentGuidance?: string;         // → MCP instructions
  oauthApp?: { registerUrl?: string; callbackPath?: string };
  provenance?: { authoredBy: string; researchedFrom?: string[]; lastReviewed?: string };
}
```

`AppSurface` (per connected way to reach the app):
```ts
{
  kind: PlatformKind,                 // "mcp"|"openapi"|"graphql"|"http"|"cli"
  displayName: string,
  connection: <the per-kind template — see 2c>,
  auth: AppAuth[],                    // which mechanisms for THIS surface; first = default.
                                      // Independent of the app-level auth[] (which is the
                                      // union across surfaces, kept for AppDefinition
                                      // back-compat). A surface's auth is NOT constrained
                                      // to be a subset — state this so a builder doesn't
                                      // invent a merge rule. groupByApp still reads the
                                      // app-level auth[] only.
  build: BuildRecipe,                 // how to construct Platform+Credential (2d)
  verify?: VerifyHint,                // DECLARATIVE only in 30.8 (see below) — 30.11 executes
  docs?: string, agentGuidance?: string,     // per-surface (durable-rich)
  // rot-prone tier (OPTIONAL + treated as "may be stale"):
  notes?: string[],                  // quirks/rate-limits — NOT load-bearing
}
```

**`VerifyHint` — define it explicitly (a doc-review caught a `<placeholder>`).** Only
ONE shipped verify primitive exists today: `OpenApiConnectionSchema.verifyOperationId`
(a string, `openapi-connection.ts:117`). There is NO shipped mcp/graphql/cli verify
field. So `VerifyHint` is a **declarative, kind-keyed discriminated union that 30.8
only VALIDATES (as data) — it does NOT run**; 30.11 wires each to a real verifier:
```ts
VerifyHint =
  | { kind: "openapi"; operationId: string }   // maps to verifyOperationId (shipped)
  | { kind: "mcp"; listTools: true }           // declarative — 30.11 lists tools
  | { kind: "graphql"; typenameProbe: true }   // declarative — 30.11 runs { __typename }
  | { kind: "none" }                           // cli/http-empty: honestly not-verifiable
```
Do NOT invent verify shapes beyond these; `none` covers anything without a real probe.

### 2c. Per-surface `connection` template — one variant per kind (discriminated on `kind`)
Each is a partial that the build recipe completes into a real add-input. Keep them
**tight to the add-INPUT shape** (§1d), not the stored connection shape, since the
recipe calls `addXPlatform`:
- `mcp`: `{ transport:"http", url } | { transport:"stdio", command, args?, tokenEnvVar?, env? }`
  (+ optional `authHeader` for http). *(Do NOT model the `header`-scheme MCP auth —
  the add-input can't set it; §5 gap.)*
- `openapi`: `{ specUrl, baseUrl?, maxTools?, select?, verifyOperationId? }`.
- `graphql`: `{ endpoint, defaultHeaders? }`.
- `http`: `{ baseUrl, defaultHeaders? }` — the request-tools come from `starterTools`
  (2e), merged into the descriptor at connect time (30.11), NOT here.
- `cli`: `{ credentialEnvVar? }` — command-tools from `starterTools`.

### 2d. `BuildRecipe` — the two mapping styles (§1d)
```ts
{
  platformIdTemplate: string,   // e.g. "{app}" or "{app}-{kind}" (multi-surface, 30.12)
  // maps this surface → an addXPlatform call:
  via: "flattened" | "descriptor",   // mcp/openapi/graphql = flattened; http/cli = descriptor
  credential: { kind: CredentialKind, from: "auth" }   // what Credential row to mint
}
```
Keep the recipe DECLARATIVE (data), not code. 30.11 writes the interpreter that reads
`via` + `connection` + `auth` and calls the right `addXPlatform`. **30.8 only DEFINES
the recipe fields + validates them; it does NOT execute them.**

### 2e. `starterTools` (user-authored surfaces only)
- For `http`: an array validated against `HttpRequestToolSchema` (import + reuse the
  SHIPPED schema — do NOT redefine request-tools). Lives in `tools/http.tools.json`.
- For `cli`: analogous, against `CliToolSchema`.
- **Gap-filler rule (§4.7):** ship starters ONLY where the surface is the recommended
  path. **GitHub ⇒ NO http starters** (OpenAPI covers REST). A spec-less app would ship them.

## 4. Migration of the 45 existing apps

- **Mechanical, lossless:** each `AppDefinition` in `catalog.ts` → a `catalog/<id>/catalog.json`
  carrying the SAME `id/displayName/supportedKinds/auth/aliases/setupHints/iconSlug`.
  `surfaces`/`help` are OPTIONAL — a migrated entry with NO surfaces is still valid
  (only GitHub gets full surfaces in THIS increment; the rest gain surfaces later/as-needed).
- **Keep `listApps()`/`getApp()` byte-identical in behavior** — same 45 ids, same
  fields present. The inc-30 **reverse-coverage regression guard** (every non-generic
  `listProviders()` entry has an app) MUST stay green.
- Delete the old `catalog.ts` array ONLY after the loader replaces it and all
  consumers (`group.ts`, web `data.server.ts readApps`) resolve through the new path.
- Write a small **one-time conversion script** to do the 45-app conversion (don't
  hand-transcribe 45 entries — mechanical error risk). Commit the generated `.json`s.

**Edge cases the migration WILL hit (doc-reviews caught these — handle explicitly):**
- **byo / none / OAuth-only apps migrate as thin, surface-less entries.** The generic
  BYO escape-hatch app (`catalog.ts:422`) and **Google** (`supportedKinds:["openapi"]`
  + `auth:[{oauth2,google}]`, **no ready surface** — the design's motivating bug) keep
  their fields with **zero `surfaces[]`**. `surfaces?` MUST be optional; the
  reverse-coverage guard (checks `auth[]` only) MUST stay green with no surfaces. Add a
  proof-of-done bullet naming **Google** (surface-less, still groups) + the byo app.
- **`help.json` merge precedence:** if a `catalog.json` has an inline `help` AND a
  sibling `help.json` exists, **`help.json` wins per-field (shallow field-merge over
  the inline base)** — decide this in the generator and document it; don't leave it
  ambiguous. (For the migration, no app has both — but the schema/loader must define it.)
- **Absent `tools/`:** a surface with no `starterTools` and no `tools/*.json` is valid
  (GitHub's http surface is exactly this). The surface template (§2c) is the *add-input*
  shape, NOT the stored `HttpConnectionSchema` (whose `tools.min(1)` would reject empty)
  — so an empty http surface template is fine; state this so the builder doesn't wire
  the surface template to `HttpConnectionSchema` prematurely.
- **fs-safe, case-insensitively-unique ids** (M1): the generator MUST reject any app id
  that isn't a safe directory name or that collides case-insensitively (macOS/Windows
  fold case; the existing case-sensitive uniqueness test won't catch `github` vs `GitHub`).
  All 45 current ids are simple slugs — this is a guard, not a fix.
- **Provenance comments** (M4): `catalog.ts:60-75` carries per-entry omission notes
  (Slack MCP unconfirmed, Notion OpenAPI, Figma none…). JSON has no comments — port the
  relevant ones into the entry's `help.provenance` (or a `help.notes[]`), don't silently drop.
- **`gen-brand-icons.mjs` dependency** (F4): that codegen imports `listApps()` for icon
  slugs — the migration must keep `listApps()` surfacing `iconSlug` so a re-run resolves.

## 5. Known gap — RECORD for 30.11, do NOT try to close in 30.8

**`oauth2` is not settable via `AddOpenApi/GraphQlPlatformInput.auth`** (`AuthInput.scheme`
is apiKey|bearer|basic only; oauth2 comes from spec-derivation — `auth.ts:11-16,50-55`).
So a catalog surface that declares `auth:[{oauth2,github}]` cannot, in a FUTURE connect
step, drive an `addOpenApiPlatform` that *sets* oauth2 — the OAuth access token is
instead injected as a **bearer** credential (which is exactly how inc-29 OAuth-over-REST
already works — the access token IS a bearer).

**30.8 cannot and should not "confirm" this empirically** — 30.8 executes NO
`addXPlatform` call (§2d, §7); there is no connect interpreter until 30.11. So a
feasibility review flagged: don't frame this as a builder proof step it can't close.
Instead:
- 30.8 only ensures the schema can **express** `credential.kind:"oauth2"` + a surface
  `auth:[{oauth2,…}]` as DATA (both are valid: `CredentialKind` has `oauth2`,
  `credential.ts:14`; `AppAuth` has `{oauth2,providerId}`, `catalog.ts:28`). No execution.
- **Record the open question in `docs/futures/revisit-when.md`** for 30.11: "does the
  build-recipe interpreter map `credential.kind:oauth2` → a bearer-injected platform the
  way inc-29 connect does, or does `addOpenApiPlatform` need an oauth2 path?" — with the
  trigger = the 30.11 connect increment.
- **The §3/§6 structural test must assert only the openapi FIELDS** (specUrl/baseUrl/
  verifyOperationId) — it must NOT route the surface's oauth2 auth through
  `buildPlatformAuth` (that errors).
