# Increment 32.3 — Master-key rotation

> Leaf slice of the 32.x wave. Builds on the 32.2-foundation crypto primitives (locked first).
> **The single hardest correctness problem in this wave:** re-encrypting the whole vault under a new
> master key has ONE unavoidable non-atomic step (you cannot atomically swap both a file and a key).
> The entire design makes that step **recoverable** — a crash at ANY point must always leave a
> `{ciphertext-file, key}` pair that opens. **A crash must never brick the vault.** That is the bar.

## §0 — What / why (scope locked)

`junction vault rotate-key` rotates the AES-256 master key that protects the **encrypted-file** vault.

**The load-bearing fact (reshapes everything):** junction has TWO secret backends, selected at runtime
by `selectStore` (`credentials/index.ts`):
- **keyring backend** — each secret stored DIRECTLY in the OS keychain by `secretRef`. The AES master
  key is NOT involved. There is no master key to rotate.
- **encrypted-file backend** — AES-256-GCM ciphertext in `credentials.enc.json`, wrapped under the
  master key (the 4-tier ladder in `master-key.ts`).

So "master key" and "the key protecting my secrets" **only coincide on the file backend**. Therefore:
- **keyring backend → REFUSE + explain** (there is no master key; nothing to rotate). Hint: if a file
  vault exists (`credentials.enc.json` present), suggest `JUNCTION_STORE=file junction vault rotate-key`.
- **file backend → proceed** with the recoverable re-key sequence below.

Backend is detected via **`store.backend`** (`store.ts:14`, `"keyring" | "encrypted-file"`) — the only
backend signal. (`createCredentialStore` already picks the backend from `JUNCTION_STORE`/auto.)

**Rotate WITHIN the key's tier — never downgrade posture.** If the operator's master key is a Tier-1
passphrase or a keyring entry, the new key reinstalls at that same tier. A rotation must never silently
move a passphrase-protected vault to an on-disk auto-key (that would weaken at-rest protection the
operator deliberately chose).

## §0a — FORK RESOLVED (user, this session): tier-1 env-raw rotation

The master key can come from `JUNCTION_MASTER_KEY` (a raw 32-byte key). junction **cannot rewrite the
operator's environment**, so it cannot reinstall a new key there. **Decision:**
- **DEFAULT: refuse + point to export/import.** On an `env-raw` tier, `rotate-key` (with no override
  flags) refuses:
  > `master key is supplied via JUNCTION_MASTER_KEY (env); junction cannot rewrite your environment.
  >  To rotate: (1) vault export --out backup.jvlt  (2) set a new JUNCTION_MASTER_KEY  (3) vault import
  >  backup.jvlt.  Refused — nothing changed.`
- **ESCAPE HATCH (user asked for it — "--print-new-key is required"): `--print-new-key --i-understand`.**
  With BOTH flags on an `env-raw` tier, junction runs the full recoverable re-key sequence, re-encrypts
  the vault under a fresh random key, and **prints the new key once** to stdout (base64) for the operator
  to set as their new `JUNCTION_MASTER_KEY` before next boot. **Footgun-aware guardrails:**
  - Both flags required (not one) — `--print-new-key` alone (no `--i-understand`) still refuses, printing
    the danger note. `--i-understand` alone does nothing.
  - The command prints, in a clearly-delimited block: the new key, and a **loud warning** that the vault
    is now encrypted under this key and the running env still holds the OLD key → **the old key must
    remain set until the operator updates it; if they lose this printed key the vault is stranded.**
  - Because the env still holds the OLD key at command exit, the **pre-rekey backup is KEPT** (see the
    sequence) so `credentials.enc.json.pre-rekey` still opens under the OLD env key as a safety net.
  - `--print-new-key` is ONLY meaningful on `env-raw`. On file/keyring/env-passphrase tiers it's rejected
    as invalid (those reinstall the key themselves; printing a key junction just installed to disk/keyring
    would be a pointless secret-on-stdout leak).
  - The `--json` output on this path includes `newKey` (base64). On EVERY other path `newKey` is absent.
    NEVER print/return the key on any tier that reinstalls it itself.

## §0b — Load-bearing facts + the RECOVERY MODEL (reworked after doc-review — 3 CRITICALs)

The doc-review (ce-feasibility, adversarial) found **three CRITICAL bricking vectors** in the first draft's
recovery design. The model below is the **corrected, provably-safe** one. The core simplification:

> **RECOVERY INVARIANT (the whole safety argument, one sentence):**
> **While the fixed-name old-key sidecar `.master.key.old` exists, a rotation is in flight and the ONLY
> authoritative openable state is `{pre-rekey ciphertext, OLD key}`; recovery ALWAYS rolls back to it.
> Success is signalled by DELETING the sidecar (the last step). So: sidecar present ⇒ roll back; sidecar
> absent ⇒ nothing to do.** No forward/backward ambiguity, no "does it decrypt under key X" guessing.

This collapses the first draft's three fragile prose branches (whose triggers didn't match the states they
claimed — CRITICAL-2) into ONE rule. Roll-back is always safe because the pre-rekey backup + old key
always exist together while the sidecar exists.

**CRITICAL-1 fix — hook placement (was skipped on the auto/keyring path):** `selectStore`
(`credentials/index.ts:45-70`) short-circuits to the keyring store at line 68 when the keyring probes
usable — so `buildFileStore` (the first draft's hook site) is NEVER called on a normal keyring-capable
machine, and a crashed `JUNCTION_STORE=file` rotation would never recover. **FIX:** `recoverInterruptedRekey`
is hoisted to run at the TOP of `createCredentialStore`/`selectStore`, BEFORE the keyring/file branch,
gated ONLY on "a `.master.key.old` sidecar exists on disk" (a single `stat`; fast-path returns immediately
when absent). It runs regardless of which backend auto-selection picks — a half-rotated FILE vault gets
recovered even when the process opens as keyring. The `vault rotate-key` CLI command ALSO calls it
defensively before starting (so a prior interrupted rotation is healed before a new one begins — this also
enforces "never two sidecars", CRITICAL/HIGH-2).

**CRITICAL-2 fix — fixed-name sidecar + missing/empty-file safety:** the sidecar is the FIXED name
`.master.key.old` (NOT `<rand>`-suffixed) so there is at most one, and a second rotation attempt refuses
until recovery clears it (kills the multi-crash ambiguity). Recovery treats an ENOENT/empty live file as
"roll back" like any other in-flight state (never as a vacuous success — the first draft's branch-1
would false-succeed on an empty `{v:1,entries:{}}` from `loadEncFile`'s ENOENT path and orphan the
pre-rekey → brick). Because recovery ALWAYS rolls back while the sidecar exists, the empty/missing-file
case needs no special decrypt test — it just restores pre-rekey + old key.

**CRITICAL-3 fix — env-passphrase old-salt preservation:** step 9 overwrites `master.key.salt` on the
env-passphrase tier; the first draft kept no old-salt backup, so an interrupted env-passphrase rotation
left the vault openable under NO key (the still-OLD env passphrase + the NEW on-disk salt derive a
useless key). **FIX:** before overwriting the salt, back it up to `master.key.salt.pre-rekey`; recovery
restores it (roll-back reinstalls the OLD salt so the still-OLD env passphrase re-derives the OLD key that
opens the restored pre-rekey ciphertext). The sidecar on env-passphrase stores the derived OLD key bytes
too (belt-and-suspenders for the smoke test), but the SALT is what the passphrase re-derivation path
actually needs.

**HIGH-1 fix — recovery must not mutate disk:** recovery must NOT call `resolveMasterKeyWithTier` on the
env-passphrase tier during its decision, because that calls `loadOrCreateSalt` which AUTO-WRITES a fresh
salt on ENOENT (`master-key.ts:140-151`) — corrupting the state recovery is trying to restore. Since the
model is "always roll back while sidecar exists," recovery does NOT need to resolve/derive any key to
decide — it just performs the deterministic file restores (rename pre-rekey→live, restore old salt,
reinstall old key from sidecar on the file tier). No key derivation, no disk mutation beyond the restores.

**MEDIUM-2 fix — no nested lock:** rotation writes go through `writeFile0600`/`rename` DIRECTLY, NEVER
through `saveEncFile` (whose `finally` unconditionally `release()`s the shared lock — `encrypted-file-
store.ts:76-77` — which would drop rotation's own lock mid-sequence). Stated so the builder doesn't reach
for `saveEncFile`.

**Other facts:**
- **No new migration** — rotation only rewrites `credentials.enc.json` + `master.key`/keyring/salt files.
- **Error kinds** `rotate-refused`/`rotate-failed` are added in the **32.2 foundation slice** (per
  spec-flow C2 — both leaves would otherwise edit the exhaustive `formatCredentialError` in parallel).
  This slice only CONSTRUCTS them.
- **The lock:** rotation acquires the SAME `.credentials.lock` (`proper-lockfile` on `paths.home`) the
  store uses, so a concurrent `set()`/rotation can't interleave. Recovery ALSO takes the lock (so a boot
  recovery and a concurrent store-open serialize).

## §1 — The recoverable re-key sequence (file backend)

`rotateMasterKey(paths, env, opts) → ResultAsync<RotateResult, CredentialError>` in a new
`packages/core/src/credentials/rotate-master-key.ts`. `RotateResult = { tier: MasterKeyTier["kind"];
rotated: boolean; backupFile: string; newKeyForOperator?: string }` (`newKeyForOperator` present ONLY on
the env-raw `--print-new-key` path).

**Filenames** (all under `paths.home`, all 0600 via `writeFile0600`; ALL FIXED names — no `<rand>` on
recovery-critical artifacts, per CRITICAL/HIGH-2):
- live: `credentials.enc.json` (= `paths.credentialsFile`)
- new tmp: `credentials.enc.json.rekey.tmp` (fixed; unlinked on abort)
- pre-rekey backup: `credentials.enc.json.pre-rekey` (the roll-back source; kept on success)
- **old-key sidecar (the in-flight flag): `.master.key.old`** (base64 of the old 32B key; 0600). Its
  presence == "rotation in flight"; its deletion == "success". FIXED name.
- old-salt backup (env-passphrase tier only): `master.key.salt.pre-rekey`.

**Sequence (numbered — recovery §2 handles a crash at ANY point via the single roll-back rule):**

0. **Heal first:** call `recoverInterruptedRekey(paths, env)` — if a `.master.key.old` sidecar exists from
   a prior interrupted attempt, roll it back BEFORE starting (so we never stack two rotations / two
   sidecars). Then proceed.
1. **Acquire `.credentials.lock`** (release in a `finally`).
2. **Resolve OLD key + TIER** via `resolveMasterKeyWithTier(paths, env)`.
   - `keyring` tier → **release lock, return `rotate-refused`** (defensive — see §0b; can't occur on a
     file store today).
   - `env-raw` tier → apply §0a policy (refuse unless `--print-new-key --i-understand`).
3. **EMPTY-VAULT branch (spec-flow C3):** if `credentials.enc.json` is ABSENT (a `JUNCTION_STORE=file`
   home where no credential was ever added — `loadEncFile` returns `{v:1,entries:{}}` on ENOENT), there is
   nothing to re-encrypt and step 8's first rename would ENOENT-throw. **Rotate the key IN PLACE:**
   install a fresh NEW key at the tier (step 9 logic only), NO file dance, NO pre-rekey/sidecar. On
   `env-raw` this still means `rotate-refused` (can't install) unless `--print-new-key`. Return
   `{tier, rotated:true, backupFile:undefined, newKeyForOperator?}`. (Lets a fresh operator pre-rotate
   before adding secrets.) A test covers "rotate empty file vault → no crash → subsequent `credential add`
   works under the new key."
4. **Load + decrypt ALL entries** from the live file under the OLD key (`EncFileSchema.parse` →
   `gcmDecrypt(oldKey, Buffer.from(secretRef), record)` per entry, into a `Map<secretRef, plaintext>`).
   **If ANY entry fails to decrypt → ABORT** with `rotate-failed` (a pre-existing undecryptable entry
   means the vault is already partly broken; rotating would silently drop it — never silently drop a
   secret). Release lock, nothing written.
5. **Generate NEW key**: `randomBytes(32)` — UNLESS `env-passphrase` tier, where the "new key" is derived
   from a **new passphrase** (see §1a) under a **fresh salt**.
6. **Re-encrypt all** entries under the NEW key into the **new tmp file** `credentials.enc.json.rekey.tmp`
   (fresh IV per entry, `aad = Buffer.from(secretRef)`, `v:1`), written 0600 via `writeFile0600`
   (NOT `saveEncFile` — MEDIUM-2).
7. **Round-trip VERIFY the tmp file under the NEW key (verify-BEFORE-swap):** re-read the tmp, and for
   **every `secretRef` in step 4's map**, `gcmDecrypt(newKey, Buffer.from(secretRef), tmpRecord)` MUST
   equal the original plaintext, AND the tmp's key-set MUST equal step 4's key-set (keyed by `secretRef`,
   NOT a bare plaintext-set compare — MEDIUM-1: identical plaintexts under different refs must not mask a
   swapped-ref record). **On any mismatch/missing ref → unlink tmp, ABORT `rotate-failed`** (nothing
   swapped; live+OLD key untouched).
8. **Write the in-flight artifacts, THEN swap** (this is the recoverable window — but recovery's single
   roll-back rule covers every sub-point):
   a. **Persist OLD key to the sidecar** `.master.key.old` (0600). *(From here, sidecar-present ⇒
      recovery rolls back.)*
   b. env-passphrase only: **back up the old salt** → `master.key.salt.pre-rekey` (0600) BEFORE step 9
      overwrites it (CRITICAL-3).
   c. **rename** live `credentials.enc.json` → `credentials.enc.json.pre-rekey`.
   d. **rename** tmp → live `credentials.enc.json`.
9. **Install the NEW key at the SAME tier:**
   - `file` → `writeFile0600(paths.masterKeyFile, newKey)`.
   - `keyring` → `Entry("junction","__master_key__").setPassword(newKey.toString("base64"))` (defensive;
     see §0b — a file store can't source its key from keyring today).
   - `env-passphrase` → `writeFile0600(paths.masterKeyFile + ".salt", newSalt)` (the passphrase re-derives
     the key next boot from the NEW salt; new passphrase from `--new-passphrase-stdin`, §1a).
   - `env-raw` → **cannot install** — the `--print-new-key` path: set `newKeyForOperator =
     newKey.toString("base64")`; write NO key file (operator installs it into their env).
10. **Verify the live vault opens under the NEW key** (smoke test): for `file`/`keyring`/`env-passphrase`,
    resolve the key the SAME way boot will (file: read master.key; keyring: getPassword; env-passphrase:
    derive from the *new* passphrase + new salt — the command has the new passphrase in hand from stdin,
    so it derives directly rather than reading the still-OLD env) and decrypt one entry. For `env-raw`,
    decrypt one entry directly with the in-hand `newKey`. **On failure → do NOT delete the sidecar; let
    recovery roll back** (return `rotate-failed`; the sidecar's presence means the next open heals it).
11. **SUCCESS: delete the sidecar `.master.key.old`** (this is the atomic "committed" signal) and, on
    env-passphrase, delete `master.key.salt.pre-rekey`. **KEEP** the pre-rekey backup
    `credentials.enc.json.pre-rekey` (0600) as the operator's safety net (fork resolved: keep). Release
    lock. Return `{tier, rotated:true, backupFile, newKeyForOperator?, pendingEnvUpdate?}`
    (`pendingEnvUpdate:true` on env-raw/env-passphrase — spec-flow I4).

### §1a — env-passphrase reinstall (`--new-passphrase-stdin`)

For the `env-passphrase` tier, the "new key" is a re-derivation under a **new passphrase + fresh salt**.
`--new-passphrase-stdin` reads the new passphrase from stdin (never argv). Step 4 becomes: fresh
`salt = randomBytes(16)`; `newKey = deriveKeyFromPassphrase(newPass, salt)`. Step 9 writes the fresh salt
to `master.key.salt`. **The operator must then update `JUNCTION_MASTER_KEY` to the new passphrase** — so
this tier ALSO surfaces a loud note (like env-raw) that the running env still holds the OLD passphrase;
the pre-rekey backup is KEPT. If `--new-passphrase-stdin` is absent on an env-passphrase tier → refuse
with a hint to supply it. (This keeps env-passphrase rotatable, honoring "rotate within tier".)

## §2 — `recoverInterruptedRekey` — the single roll-back rule (the correctness heart)

**The reworked model has ONE rule, not three branches.** The `.master.key.old` sidecar is the in-flight
flag; step 11's deletion of it is the atomic "committed" signal.

```
recoverInterruptedRekey(paths, env):
  if not exists(.master.key.old):            # FAST PATH — the only cost on a normal boot (one stat)
      return                                  # no rotation in flight; nothing to do
  acquire .credentials.lock                   # serialize with any concurrent open
  # A rotation was interrupted at SOME point in steps 8a–10. Roll BACK deterministically —
  # NO key derivation, NO decrypt test, NO disk mutation beyond these restores (HIGH-1):
  if exists(credentials.enc.json.pre-rekey):
      atomically rename credentials.enc.json.pre-rekey -> credentials.enc.json   # restore OLD ciphertext
  # (if pre-rekey is absent, the swap (8c) hadn't happened yet: the live file is still the OLD ciphertext
  #  — leave it. Either way the live file is now the OLD ciphertext.)
  unlink credentials.enc.json.rekey.tmp  (best-effort)                            # drop the half-written NEW file
  # Reinstall the OLD key at its tier so the OLD ciphertext opens:
  oldKey = read(.master.key.old)  (base64 -> 32B)
  file tier:            writeFile0600(master.key, oldKey)                         # restore OLD key file
  keyring tier:         Entry("junction","__master_key__").setPassword(oldKey_b64)  # defensive
  env-passphrase tier:  if exists(master.key.salt.pre-rekey):
                            rename master.key.salt.pre-rekey -> master.key.salt    # restore OLD salt (CRITICAL-3)
                        # env still holds the OLD passphrase -> OLD passphrase + OLD salt = OLD key -> opens OLD ciphertext
  env-raw tier:         # nothing to install — env still holds the OLD key -> opens the restored OLD ciphertext
  delete .master.key.old                                                          # clears the in-flight flag
  release lock
  log.warn("recovered an interrupted master-key rotation; the vault was rolled back to its pre-rotation state")
```

**Why this is provably safe at EVERY crash window (the guarantee):**
- The sidecar is written FIRST (8a), before any destructive step. So a crash BEFORE 8a leaves no sidecar →
  no rotation ever "started" from recovery's view → the live file is still OLD ciphertext under the OLD
  installed key → opens. ✓
- A crash ANYWHERE in 8a–10 leaves the sidecar present → recovery rolls back: it restores the OLD
  ciphertext (from pre-rekey if the swap happened, else it's already OLD) and reinstalls the OLD key/salt
  → the OLD ciphertext opens under the OLD key. ✓  (This holds whether the live file is the NEW file, the
  OLD file, or momentarily ENOENT between the two renames — recovery doesn't test-decrypt; it
  deterministically makes {live = OLD ciphertext, installed = OLD key}.)
- A crash AFTER 11 (sidecar deleted) → fast path, no-op → the NEW ciphertext under the NEW key opens
  (rotation genuinely completed). ✓
- **Idempotent:** running recovery twice is safe — after the first run the sidecar is gone, so the second
  run is the fast-path no-op. A recovery that runs after a genuine success is also the no-op (sidecar
  already deleted) — it can NEVER roll back a completed rotation (this closes the first draft's MEDIUM-3
  where a branch-1 false-negative could destroy a good NEW vault).

**env-raw / env-passphrase note:** on a roll-back the running env still holds the OLD key/passphrase, and
recovery restores the OLD salt (env-passphrase) — so the OLD env value opens the restored OLD ciphertext.
The operator simply re-runs `vault rotate-key`. The `--print-new-key` success path is the ONLY case where
the operator must update their env; a crash before success always rolls back to the still-current OLD env
key. This is why the pre-rekey backup is KEPT even on success (extra safety net), and the sidecar+old-salt
are deleted (success committed).

## §4 — Tests (adversarial crash-injection is MANDATORY)

Core `rotate-master-key.test.ts` (harness: `withTempHome` + `createEncryptedFileStore` + seed several
credentials via `store.set`), driving the REAL sequence:

**Happy path (file tier):**
- Seed 3 secrets → rotate → all 3 still resolve (decrypt under the NEW key); `master.key` bytes CHANGED;
  `credentials.enc.json` ciphertext CHANGED (new IVs); pre-rekey backup exists + opens under the OLD key;
  sidecar deleted; perms 0600 on new file + master.key + backup.

**Crash injection (the mandatory adversarial set)** — inject a thrown error / early-return at each step
boundary via a test seam (an injectable `afterStep?: (n:string)=>void` hook on `rotateMasterKey`, or split
the sequence into testable steps), then run `recoverInterruptedRekey` + open the store and assert
**every credential still resolves**. Under the single roll-back model, the assertion after a mid-sequence
crash is **"all secrets open under the OLD key (rolled back)"**; after a post-step-11 crash it's "all open
under the NEW key":
- Kill after step 6 (tmp written, sidecar NOT yet written) → no sidecar → recovery no-op; recovery/next-open
  cleans the stray tmp; all open under OLD key (nothing swapped).
- Kill after 8a (sidecar written) but before 8c (renames) → recovery rolls back (pre-rekey absent → live is
  still OLD ciphertext; reinstall OLD key; delete sidecar); all open under OLD key.
- Kill BETWEEN the two renames 8c/8d (live is momentarily ENOENT) → recovery rolls back (rename pre-rekey→
  live restores OLD ciphertext); all open under OLD key. **(This is the window the first draft mishandled.)**
- Kill after 8d (swap done) before 9 (key install) → recovery rolls back to pre-rekey + OLD key; all open.
- Kill after 9 (new key installed) before 11 (sidecar still present) → recovery STILL rolls back (sidecar
  present ⇒ roll back; it reinstalls the OLD key over the just-installed NEW key + restores OLD ciphertext);
  all open under OLD key. (Rolling back a nearly-complete rotation is safe and correct — the operator
  re-runs; we never leave a half state.)
- Kill after 11 (sidecar deleted) → recovery no-op; all open under the NEW key (genuine success).
- **Corrupt the new tmp file before step 7** → step 7 verify (secretRef-keyed) catches it → ABORT, no
  sidecar written, nothing swapped, all open under OLD key (verify-before-swap proven).
- **Pre-existing undecryptable entry** (hand-write a bad record) → step 4 ABORTS, nothing written.
- **Identical-plaintext-different-ref** two credentials → step 7's secretRef-keyed compare still passes on a
  correct rotation and FAILS on a hand-swapped-ref tmp (MEDIUM-1 regression).

**Idempotency + heal-before-start (MEDIUM-3 / HIGH-2):**
- Run `recoverInterruptedRekey` TWICE after an injected crash → second run is the fast-path no-op; all open.
- Run `recoverInterruptedRekey` after a GENUINE success (sidecar already deleted) → no-op; the NEW vault is
  NOT rolled back (proves recovery can never destroy a completed rotation).
- Two rotation attempts (crash, then re-run) → step 0 heals the first before the second starts; never two
  sidecars; all open.

**Empty-vault (spec-flow C3):**
