# Increment 32.6b — Real `/audit` web page

> Second of the **32.6 web dogfooding fixes**. The audit LOG backend shipped inc 31 (`junction audit`
> reads `<home>/audit.log`), but the web `/audit` page is still a ComingSoon stub. This makes the
> shipped audit log visible + filterable in the browser.

## §0 — What / why (scope locked)

Replace the `/audit` ComingSoon stub (`web/src/routes/audit.tsx`) with a real page that reads the audit
log and shows a filterable table — mirroring the CLI `junction audit` filters
(`--profile`/`--key`/`--tool`/`--since`/`-n`).

**The one architectural constraint (verified):** the read/filter logic lives ONLY in the CLI
(`cli/commands/audit.ts`), and **web cannot import cli** (sibling apps). So this slice is internally
**two ordered steps**:
- **B1 (core, lands first):** extract `readAuditLog` + `filterAuditEntries` + `AuditFilters` +
  `parseSinceUtc` into a NEW `core/src/audit/read.ts`; rewire the CLI onto it (dedup — the CLI keeps only
  its human formatter + arg parsing).
- **B2 (web, after B1):** a server-fn + `audit.server.ts` reader (server-only, imports the core reader +
  `getPaths`) + the route rebuilt with a `useTableView` table.

**Scope:** read + filter + display. **NOT** in scope (deferred, already in the backlog): audit-log
**rotation** (`audit.log` grows unbounded), a SQLite `audit_events` table, `--audit-args`, listTools
auditing. **Tail, don't slurp at scale** — see §0b.

## §0b — Load-bearing facts (verified against the real code)

- **No reader exists in core today** — `core/src/audit/` has `schema.ts` + `redact.ts` + `sink.ts` only.
  The barrel (`core/src/index.ts:5-15`) exports the schema/redact/sink but NO `readAuditLog`. So B1 is a
  genuine extraction, not a move-within-core.
- `readAuditLog(filePath) → Promise<{entries: AuditEntry[]; skipped: number}>` (`audit.ts:27-57`):
  `readFile`; ENOENT → `{entries:[],skipped:0}`; split `\n`; `JSON.parse` + `AuditEntrySchema.safeParse`
  per non-blank line; malformed → `skipped++`, skipped, never fatal. Move VERBATIM to core.
- `AuditFilters` (`audit.ts:70-76`) = `{profile?,key?,tool?,since?,limit}`. `filterAuditEntries(entries,
  filters) → {filtered, sinceError}` (`audit.ts:82-109`): profile matches `e.target.profile ===
  filters.profile || e.principal.profiles.includes(filters.profile)`; key→`e.principal.keyId`;
  tool→`e.target.tool`; since→`Date.parse(e.ts) >= sinceMs`; then **tail** `limit>0 ? slice(-limit) :
  filtered`. `parseSinceUtc(since) → number|null` (`audit.ts:65-68`). Move VERBATIM.
- The CLI's `formatHuman` (`audit.ts:111-138`) is CLI-only presentation — STAYS in cli.
- `AuditEntry` (`schema.ts:50-68`) is **metadata-only** (v/ts/event/correlationId/principal/target/
  argKeys/argHash/durationMs/outcome/errorKind) — **NO secrets, no arg values** (that's the inc-31
  contract). So it can go straight to the client, matching the metadata-only DTO rule other loaders
  follow — **no redaction step needed** (but DO map to a DTO shape rather than returning the raw type, to
  stay consistent with the "never return a core type directly" web convention).
- `getPaths().auditLogFile` = `<home>/audit.log` (`paths/index.ts:22,51`), already exported.
- **Unbounded-log caveat:** the CLI does `readFile` of the whole file then tails last N. For a long-lived
  `serve` the log can grow large. For B2, cap the read: read the file and tail, but **guard the read**
  (e.g. if the file exceeds a byte cap, read only the last N bytes / lines from the end rather than
  slurping all — a `tailFile(path, maxBytes)` helper). This keeps the web loader bounded. (A full
  rotation solution stays deferred.) The CLI can keep its slurp (interactive, one-shot).

## §2 — B2: the web page (AFTER B1 locks)

**NEW `packages/web/src/server/audit.server.ts`** (server-only; imports `@junction/core`):
```ts
// SPDX-License-Identifier: AGPL-3.0-only  (server-only — imports @junction/core; called only from a server-fn)
import { getPaths, readAuditLogTail, filterAuditEntries, type AuditFilters, type AuditEntry } from "@junction/core"

export interface AuditEntryDTO { ts: string; principalKind: "api-key"|"stdio"; keyId: string|null; label: string|null; profile: string; namespace: string; tool: string; argKeys: string[]; durationMs: number; outcome: "ok"|"error"; errorKind: string|null }
export interface AuditReadResult { entries: AuditEntryDTO[]; skipped: number; truncated: boolean; total: number }

export async function readAudit(filters: AuditFilters): Promise<AuditReadResult> {
  const AUDIT_TAIL_CAP = 2 * 1024 * 1024   // bound the web read (rotation deferred)
  const { entries, skipped, truncated } = await readAuditLogTail(getPaths().auditLogFile, AUDIT_TAIL_CAP)
  const { filtered } = filterAuditEntries(entries, filters)
  return { entries: filtered.map(toDto), skipped, truncated, total: entries.length }
}
```
- `toDto(e: AuditEntry) → AuditEntryDTO` — flatten principal/target to the columns the table needs;
  metadata-only (no argHash even — argKeys is enough for display; keep it lean). Never returns the raw
  core type (the web convention).

**Decision (B2, I own it):** default the loader to `{limit: 200}` (a sane page-worth over the tail) and
apply finer filters client-side in the table (search/sort/paginate via `useTableView`), OR pass the
route's search params as `AuditFilters` to the server-fn. **Recommend: server-fn takes the coarse tail +
optional `since`/`limit`; the table does profile/key/tool/text filtering client-side via `useTableView`**
(matches how `/credentials` filters client-side over a loaded set) — simpler, and the tail is already
bounded. (If the log is huge, `since` narrows server-side.)

**NEW server-fn in a NEW `packages/web/src/server/audit.functions.ts`** (a dedicated file — NOT
`data.functions.ts` — so this slice shares ZERO files with 32.6a, which touches `data.functions.ts`'s
neighbourhood; keeps the worktree merge conflict-free): a `GET` `createServerFn` `getAudit` with a
`.validator` for the optional `{since?, limit?}` and a `.handler` that calls `assertLocalHost()` then
`readAudit(...)`. Re-export `AuditEntryDTO`/`AuditReadResult` by type from `audit.functions.ts`. (This
mirrors the existing `*.functions.ts` conventions; a dedicated audit module is clean and collision-free.)

**REBUILD `packages/web/src/routes/audit.tsx`:** drop the ComingSoon stub. Add a `loader` calling
`getAudit(...)`; render a `PageHeader` (no ComingSoon), a filter bar (search + facet Selects for
outcome/tool/profile via the shared `FacetSelect`/`useTableView` pattern from `credentials.tsx`), and a
table (columns: Time (UTC, pinned `Intl.DateTimeFormat` per the SSR-flicker gotcha), Principal
(key label / stdio), Profile, Namespace·Tool, Args (argKeys count or chips), Duration, Outcome (a
badge: ok / error+errorKind)). Empty log → an honest EmptyState ("No tool calls recorded yet — once an
agent calls a tool through `junction serve`, it appears here."). `truncated` → a subtle "showing the most
recent N" note.

## §3 — Design (I own this; follow the Geist system)

Reuse the established table surface: the `/credentials` table primitives (`useTableView`, group-divider
rows, mono cells, sortable headers, pagination, `FacetSelect`), the badge taxonomy (ok = the Connected-
style positive chip; error = the Auth-Failed-style negative chip with the `errorKind` as the caption),
Geist-Mono for the tool/keyId cells. **Time column uses the pinned UTC `Intl.DateTimeFormat`** (the
inc-27 SSR-hydration-flicker gotcha — `keys.tsx formatDate` is the reference). No new visual language —
this is the audit surface finally rendered on the existing system. The nav item + `/audit` route already
exist; just swap the component.
