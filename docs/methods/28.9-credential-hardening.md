# Method File 28.9 — Credential hardening: real kinds + verify-on-add

> **Make the credential layer honest before OAuth builds on it.** Today the schema allows
> `["api-key","bearer","oauth2","file","env"]` but the add-paths hard-gate to `bearer`, and
> `Credential.kind` is **decorative at runtime** (injection is driven entirely by the
> platform's `auth` descriptor) — so an API key stores labeled "bearer", and a stdio-MCP
> env-injected token stores labeled "bearer". Meanwhile a stored token is never tested:
> a wrong/expired token shows "Configured" forever, though the badge taxonomy has had
> `connected`/`auth-failed`/`expiring` **reserved since inc 23**. This increment ships the
> real kind set the user chose (**api-key, bearer, env, file**; oauth2 stays gated for inc 29)
> and **verify-on-add / test-connection** — honestly, per source kind.
>
> **Audit grounding (verified in code, this session):** the *injection* layer is already
> complete (apiKey header/query/cookie + bearer custom-header + basic + oauth2-as-bearer in
> `openapi-client/http.ts:96-130`; MCP http bearer; MCP stdio `tokenEnvVar`; CLI
> `credentialEnvVar` sandbox-scrubbed env). The gaps are: the kind gate, the kind↔platform
> validation void, no verify anywhere, MCP's hardcoded `Bearer ` prefix (`connect.ts:110`),
> and no file-credential mechanics.

---

## ⚠️ Decisions taken while the user was away (CONFIRM at the step-4 gate)

The user approved the hardening and the kind set (*"we need to ensure we support api-key,
bearer, file, env and then oauth2. We should also have verify-on-add/testconnection"*), then
was away for the four design forks. Proceeded on the recommended option for each — all
flagged here for override:

1. **`file` kind is IN, as a separable slice (D)** — the one piece with new mechanics; it
   lands last in the wave and may slip to a follow-up without blocking A–C.
2. **Verification state is PERSISTED** — `lastVerifiedAt` + result on the credential row
   (additive migration 0008) → the credentials page shows *"Connected · checked 2h ago"* /
   *"Auth Failed"* honestly. (Alternative was action-only/toast — rejected: badges would stay
   "Configured" forever and the dashboard couldn't surface broken credentials.)
3. **OpenAPI verify = operator-designated `verifyOperationId`** (optional descriptor field;
   a safe cheap GET like `/user` chosen at platform-add). If unset → honestly
   *"not auto-verifiable"*. (Rejected: auto-picking a GET — junction silently firing a
   request the operator never chose is wrong for a security-focused broker; rejected:
   no OpenAPI verify at all — the most common source kind deserves a story.)
4. **MCP raw-header fix is IN** — additive `header` auth variant so a server wanting
   `X-Api-Key: <raw>` (no `Bearer ` prefix) is expressible.
5. **`basic` auth is DEFERRED** (the user's kind list omits it — treated as intentional).
   Recorded in `revisit-when.md` with the username-modeling problem it carries
   (username lives platform-level today, breaking the multi-account wedge for basic).

**Post-review:** a feasibility review then corrected the plan on 6 points (all folded in):
the false "callers fetch the platform" premise → `addCredential` owns a `platform` param;
slice D's kind-threading ripple + `callTool` try/finally restructure named as real work;
the GraphQL 401/403→auth-failed mapping does NOT exist (budgeted, + the 200-with-errors
shadow path decided); no CLI `platform edit` exists (verify-op edit goes through the web
edit form); journal gate = "new > max"; file cap 64→32 KiB (Linux keyutils ceiling).

## Part 1 — Spec (what & why)

### The kind model (the load-bearing design decision)

`Credential.kind` describes **the shape + lifecycle of the stored secret**, not the injection
mechanism (which stays the platform descriptor's job):

| kind | Stored secret | Injection (existing mechanics) | New in 28.9 |
|---|---|---|---|
| `bearer` | one opaque token | HTTP `Authorization: Bearer` / custom header | gate stays open |
| `api-key` | one opaque key | apiKey header/query/cookie; MCP raw header | **gate opens** |
| `env` | one opaque value | child-process env var (`credentialEnvVar` / `tokenEnvVar`) | **gate opens** (labeling honesty — zero new mechanics) |
| `file` | **file content** (multiline, ≤64 KiB) | materialized to a 0600 temp file; `credentialEnvVar` carries the **path** | **new mechanics** (slice D) |
| `oauth2` | multi-ref (access+refresh) | — | stays gated → inc 29 |

### Kind↔platform compatibility (validated at add time, derived by default)

New core module `packages/core/src/credentials/kind-compat.ts`:
`compatibleCredentialKinds(platform: Platform): CredentialKind[]` — the single matrix both
add-paths and the UI consume:

| Platform auth | Compatible kinds (first = default) |
|---|---|
| openapi/graphql `auth.scheme: "bearer"` \| `"oauth2"` | `[bearer]` (oauth2 joins in inc 29) |
| openapi/graphql `auth.scheme: "apiKey"` | `[api-key]` |
| openapi/graphql `auth.scheme: "basic"` | `[bearer]` (password-as-opaque-token; basic deferred — see revisit-when) |
| openapi/graphql no auth | `[]` (no credential accepted — public source) |
| mcp http `auth.scheme: "bearer"` | `[bearer]` |
| mcp http `auth.scheme: "header"` (NEW) | `[api-key]` |
| mcp stdio (`tokenEnvVar`) | `[env, bearer]` (bearer = legacy back-compat; new adds default `env`) |
| cli (`credentialEnvVar`) | `[env, file, bearer]` (bearer legacy; default `env`) |

- **Back-compat: no data migration.** Existing rows keep their stored kind; and because
  every historical credential is kind `bearer` (the old gate), **validation accepts
  `bearer` for EVERY platform shape as documented legacy** (`isKindAccepted` = matrix ∪
  `{bearer}`), while **derivation** (the default) always picks the honest kind from the
  matrix. Explicitly wrong kinds (e.g. `env` on an openapi platform) are rejected;
  `oauth2` is rejected everywhere until inc 29. Nothing re-labels existing data.
- **UX: kind is derived by default.** `credential add` without `--kind` picks the matrix's
  first entry for the platform; an explicit `--kind` outside the matrix → clean
  `kind-incompatible` error naming the allowed set. Web add-dialog shows a Select
  pre-filtered to the matrix (replacing the disabled "bearer" input).
- **The seam (DECIDED — feasibility review corrected a false premise):** neither add path
  fetches the platform today (CLI `credential.ts:135` and web `mutations.server.ts:85` both
  hardcode `kind: "bearer"` with no `platforms.get`), and `AddCredentialInput.kind` is the
  literal type `"bearer"`. So: **`addCredential` gains a `platform: Platform` parameter**
  (a deliberate core API change; only two in-repo call sites) and performs the matrix
  validation ITSELF — kind-compat is security-relevant validation and must not live
  duplicated at the edges. Both add paths gain a `platforms.get` fetch (which also powers
  the derived-default kind). `AddCredentialInput.kind` widens to
  `Exclude<CredentialKind, "oauth2">` (oauth2 stays gated with a clear error until inc 29).

### Verify-on-add / test-connection (honest per source kind)

New in **`@junction/source-runtime`** (it composes `buildProvider` — can't live in core):
`verifyCredential(platform, secret, opts) → ResultAsync<VerifyOutcome, UpstreamError>` where

```ts
type VerifyOutcome =
  | { status: "ok" }                                   // real authenticated round-trip succeeded
  | { status: "auth-failed" }                          // upstream said 401/403
  | { status: "unreachable"; detail: string }          // network/spawn failure — NOT an auth verdict
  | { status: "not-verifiable"; reason: string }       // honest: this source kind can't be safely checked
```

**The honesty matrix (do NOT blur these):**

| Source kind | Verify action | Verdict quality |
|---|---|---|
| MCP http | `initialize` + `listTools` via `buildProvider` | **real** — authenticated round-trip; `connect.ts` already maps 401/403 → `auth-failed` (verified: `isAuthError`, connect.ts:36-58) |
| MCP stdio | spawn + `listTools` | **real** (runs the local binary — acceptable; it's what serving does) |
| GraphQL | `graphql_query` with `{__typename}` | **real**, side-effect-free — but the 401/403→`auth-failed` mapping **does NOT exist today** (feasibility-verified: `graphql-client/http.ts:216-221` maps all non-200 to `call-failed`). **Budgeted work in slice A:** add the auth-failed branches (mirror connect.ts's status check) in both the body and no-body paths + tests. **Shadow path (decide explicitly):** a server returning HTTP 200 + an `errors` array for bad auth comes back as `Ok(ToolResult{isError:true})` — map to `auth-failed` ONLY if the errors text matches the auth heuristic (unauthorized/forbidden/401/403, same as `isAuthError`); else → `unreachable` with detail (honest indeterminate — never a fake green OR a fake red) |
| OpenAPI | **only if** `connection.verifyOperationId` is set: call that op with `{}` | **real** when designated; else → `not-verifiable` ("set a verify operation on the platform"). **Mapping is a string-parse, not a typed error** (feasibility-verified: a 401 through the openapi provider is an `Ok` ToolResult with text `"401 Unauthorized\n<body>"`, `isError:true` — `openapi-client/http.ts:379-383`). `verifyCredential` parses the leading `NNN ` status from the ToolResult text: 2xx → `ok`, 401/403 → `auth-failed`, else → `unreachable`. The body is DISCARDED immediately (never persisted/returned) |
| CLI | none (running a command has side effects) | always `not-verifiable` |

- **OpenAPI `verifyOperationId`** (new optional field on `OpenApiConnectionSchema`, additive):
  validated at add/edit time — must resolve to a **GET with no required parameters** in the
  spec, else rejected with a clear error. The validation lives in
  **`@junction/platform-orchestration`** (the parsed spec is in hand at add time —
  `openapi.ts:57` — and the lib already serves both cli and web). Surfaces: CLI
  `platform add --verify-op <opId>` (**add-time only — there is NO CLI `platform edit`
  command and this increment does NOT add one**; feasibility-verified); the **web platform
  edit form** (which DOES exist, inc 26) gets the field for openapi platforms — that's the
  edit path. Edit-time re-validation reads the cached spec (`~/.junction/openapi/<id>.json`).
- **`listTools` on OpenAPI is spec parsing — NO network.** It must NEVER be presented as
  verification. This is the fake-green trap the whole design guards against.

**Persistence (migration 0008, additive):** `credentials` gains
`last_verified_at` (ms epoch, nullable) + `last_verify_result` (text enum
`ok|auth-failed|unreachable`, nullable — `not-verifiable` is NOT persisted; it's a property
of the platform, not an event). Recorded by `credential add --verify`, `credential test`,
and the web actions. Drizzle-generated (never hand-authored), journal monotonic.

**Badge mapping (web credentials page — makes the reserved taxonomy real):**
`ok` → **Connected** (+ "checked <relative time>" via the pinned-UTC formatter — the inc-27
SSR-hydration rule) · `auth-failed` → **Auth Failed** · `unreachable` → stays **Configured**
(+ tooltip "last check couldn't reach the source") · never-verified / not-verifiable →
**Configured** (+ "not auto-verifiable" note where applicable). **`connected` is only ever
rendered from a persisted real verify** — never inferred.

**Surfaces:**
- CLI: `credential add --verify` (opt-IN; never blocks storing — a failed verify still
  stores, prints the outcome, sets the row state) · `credential test --id <id> [--json]`.
- Web: add-dialog gains a "Test connection" checkbox (default ON where the platform is
  verifiable, hidden where not) · credentials-row ⋯ gains **Test Connection** · badges wired.

### MCP raw-header auth (the `Bearer ` prefix fix)

`McpConnection` http `auth` becomes a discriminated union (additive):
`{ scheme: "bearer", header? }` (unchanged, still emits `Bearer <token>`) **|**
`{ scheme: "header", name: string }` (NEW — emits the raw secret in header `name`,
no prefix). `connect.ts:106-111` gains the second branch. CLI/web platform-add for mcp/http
expose it. Regression: existing bearer behaviour byte-identical.

### `file` kind mechanics (slice D — separable, and BIGGER than it looks)

> **Scope honesty (from the feasibility review):** D is a *rewrite-plus-plumbing* slice, not
> a bolt-on. Two named work items beyond the mechanics below:
> 1. **Kind-threading through the pipe.** `resolveCredentialSecret` fetches the credential
>    row but **discards `kind`** (`resolve-credential.ts:46-73`), and
>    `buildProvider(platform, secret: string | null, paths)` is shared by all four source
>    kinds. Threading kind to `createCliProvider` changes: `resolve-credential.ts` (return
>    `{ secret, kind, account }`) → `resolve-provider.ts` → `build-provider.ts` (secret
>    param becomes `{ kind, value } | null` for the cli branch; other branches read
>    `.value`) → every caller: `cli/commands/debug.ts` (×2 call sites), the serve paths,
>    `web/server/probe.server.ts` (via makeResolveProvider), and `verifyCredential`.
>    Mechanical but wide — the builder brief must own it, byte-identical behaviour for
>    non-file kinds proven by the existing tests passing unchanged.
> 2. **`callTool` restructure (SECURITY-CRITICAL).** The cli provider's `callTool` is a
>    sync prelude + neverthrow combinator chain (`provider.ts:119-230`); materialization is
>    async and cleanup must run on ok/err/throw — neverthrow has **no `.finally`**. The
>    builder restructures it to the `new ResultAsync(work())` + `try/finally` pattern while
>    preserving ALL six documented invariants in that file (secret only in
>    `policy.env[credentialEnvVar]`, never argv/logs/results; output byte cap; kill-group;
>    etc.). `junction-sandbox-security` is the LEAD reviewer for exactly this.

- **Store:** file **content** stored via the existing CredentialStore (string; enforce a
  **32 KiB cap** at add time — fits macOS Keychain AND Linux keyutils' ~32 KiB item ceiling
  (feasibility advisory: @napi-rs/keyring backends have per-item limits; Windows CredWrite
  is ~2.5 KiB but Windows isn't a sandbox target today — note in gotchas). Service-account
  JSONs ~2.4 KiB and typical kubeconfigs fit comfortably. A store write failure surfaces as
  the existing typed store error — never a silent truncate.) CLI:
  `credential add --kind file --secret-file <path>` (reads the file, stores content —
  the path itself is NOT stored) or `--secret-stdin`. Web: a textarea/file-input.
- **Materialization (call time, CLI sources only):** in `createCliProvider`'s call path,
  when the credential kind is `file`: `mkdtemp` a fresh per-call dir → write the content at
  `0600` (`writeFile(..., { mode: 0o600 })` — the inc-6 no-chmod-after rule) → add that dir
  to the call's sandbox **readPaths** → set `policy.env[credentialEnvVar] = <the file path>`
  (the SAME descriptor field: `env` kind rides the value, `file` kind rides the path) →
  **delete the dir in a `finally`** (best-effort; note the residual like removeCredential's
  reverse-orphan note).
- **Provider signature:** decided above (work item 1) — `secret` becomes
  `{ kind, value } | null` threaded from `resolveCredentialSecret` through `buildProvider`;
  the other three source kinds' *provider code* is untouched (they consume `.value`), but
  the **pipe feeding them changes** — regression = their existing tests pass unchanged.
- **Sandbox invariants hold:** the temp path goes through `validatePolicy` (SBPL metachar
  guard); content never in argv/logs; the file lives only for the call's duration.
- Non-CLI platforms reject kind `file` via the matrix.
- Verify for file creds: `not-verifiable` (CLI source).

### Security / robustness invariants (the review gate checks these)

- **Secret discipline unchanged and extended:** file *content* is a secret — never in argv,
  logs, error causes, tool results, or any web response; the materialized path may appear in
  the child env only. Verify outcomes carry **no secret and no request URL** (the OpenAPI
  verify call reuses the leak-safe `"status\nbody"` path; outcome maps to the enum, body is
  DISCARDED — never persisted, never returned to the web).
- **Verify never blocks storing.** A failed/unreachable verify stores the credential and
  reports honestly. (An operator adding a token for a currently-down service must not be
  stuck.)
- **No fake greens:** `connected` renders only from a persisted `ok`; OpenAPI without
  `verifyOperationId` and all CLI sources surface `not-verifiable` honestly.
- **Back-compat:** existing credentials (all kind `bearer`) keep working everywhere —
  the matrix accepts legacy `bearer`; no data rewrite; `mcp serve`/`serve`/probe/call
  byte-identical for existing data.
- **Migration 0008 additive only** (two nullable columns; drizzle-generated).
- **Web boundary:** all new server logic in `*.server.ts` reached only inside `.handler()`;
  verify runs server-side via source-runtime (already a web dep — inc 28); leak gates hold.
