## Fix 1 — oauth2 verify-state dropped on vault import (a real bug)
`addOAuthImportedCredential` (import-vault.ts:1015) does `create()` but NEVER calls `setVerifyState` — unlike the non-oauth `addImportedCredential` (:892). So an imported oauth2 credential always shows never-verified → spurious reconnect/re-verify prompts. Fix: after the successful `create()` at :1015-1023, mirror the non-oauth path (best-effort, swallow failure):
```ts
if (mc.lastVerifyResult !== undefined && mc.lastVerifiedAt !== undefined) {
  await repos.credentials.setVerifyState(createResult.value.id, mc.lastVerifyResult, mc.lastVerifiedAt)
}
```
This covers BOTH strict and non-strict (same code path — strict wraps it in the journaling decorators; confirm the decorated repo's setVerifyState is journaled/compensated correctly so a strict abort still rolls it back — if setVerifyState mutates a row this import created, the row-delete compensates it transitively; verify). Test: import an oauth2 credential whose manifest carries `lastVerifyResult:"ok"`+`lastVerifiedAt` → after import the credential's verify state round-trips (not never-verified). Add it beside the existing bearer parity test (~import-vault.test.ts:1051).

## Fix 2 — widen resolve-provider kind-gate to all 5 kinds
`resolve-provider.ts:84` gates to `mcp`/`openapi` only (`unsupported-source-kind` for the rest), while `build-provider.ts` already dispatches mcp/openapi/graphql/http/cli. So code-mode/probe over a graphql/http/cli source can't resolve a provider through this path. Fix: widen the gate + the auth-presence check (:95-110) to handle all 5 kinds the way build-provider does — resolve the credential secret with the right `ResolvedSecret{kind}` (cli needs the CliSecret env/file handling build-provider knows; graphql/http read the value only). PREFER consolidation: if resolve-provider and build-provider now do near-identical kind dispatch, factor the shared kind→provider logic so they can't drift (rule-of-three judgment — if it's genuinely 2 near-identical switches, extract; if the auth/secret-resolution differs enough, keep them separate with a shared helper for the secret-resolution part). Do NOT change build-provider's behavior. Tests: resolve-provider builds a provider for a graphql source, an http source, and a cli source (previously `unsupported-source-kind`); mcp/openapi unchanged.

## Fix 3 — unwrap tools.search()/describe.tool() facade results
Slice F unwrapped direct `tools.<ns>.<tool>()` results into usable values but LEFT the discovery helpers (`searchFacade`/`describeFacadeTool` in facade.ts) returning raw JSON STRINGS the guest must `JSON.parse` itself. Fix: the guest-side `tools.search(...)` and `tools.describe.tool(...)` return a usable OBJECT (parsed), matching the F ergonomics. The host builds the structured value; the guest wrapper parses it through the SAME null-proto reviver F uses (prototype-pollution guard). Update the `RESULT_SHAPE_GUIDANCE` / `describe()` doc + the run_code tool description to state search/describe now return objects too. Test: guest code does `const hits = await tools.search({query:"x"}); hits[0].name` (usable, not a string); `const d = await tools.describe.tool({...}); d.inputSchema` usable. Keep the existing F direct-call unwrap tests green.
