## 0. TL;DR for the builder

Today `/app/:id` (`packages/web/src/routes/app.$id.tsx`) shows each catalog surface
surface-first (inc 30.10), and an **unconnected** surface (`surface.connections.length ===
0`, `app.$id.tsx:415`) renders only an empty tools panel — **no "Connect" affordance**.
This increment adds one: a **Connect `<surface>`** button per unconnected surface that
reads the catalog's build recipe **server-side**, pre-fills a confirm dialog, and — on the
user's explicit confirmation — stands up the Platform + Credential through the **existing
validated path**, gated by verify so a wrong guess leaves **nothing** persisted in the DB.

**The build recipe already exists** — inc 30.8 shipped `BuildRecipeSchema`
(`catalog-schema.ts:122`) + `AppSurfaceConnectionSchema` (`:62`) as declarative data on
every `AppSurface`. 30.11's job is to **interpret** it, not design it.

### THE SCOPE DECISION (doc-review, load-bearing): token-mode connect only

Doc-review (ce-feasibility Finding 1 + ce-spec-flow C1) proved **oauth2-mode one-click
connect is not implementable from the catalog recipe**: the inc-29 OAuth start
(`startConnect`, `oauth-connect.server.ts:39`) **hard-requires BYO `clientId` /
`clientSecret` / `scopes`** that the user registers with the provider — the recipe carries
only `providerId`. There is no ambient junction OAuth app. So oauth2 connect is a
multi-field registration form, not one-click.

**Decision:** **30.11 ships the token/api-key path only.** For a surface whose chosen auth
is oauth2, the Connect button is a **deep-link hand-off** to the existing inc-29
`/credentials` OAuth registration flow (pre-selecting the provider where the route
supports it) — NOT an inline connect. This is honest, ships real value (GitHub REST/GraphQL
via a PAT is the exact QA proof), and de-risks the increment. **Inline catalog-seeded
oauth2 connect is deferred** to a later increment (record in §9 — trigger: a decision on
whether junction ships/brokers an OAuth app, or the inc-29 form gets a catalog-seeded
variant).

### The four load-bearing facts (research-confirmed 2026-07-06)

1. **The recipe is `{platformIdTemplate, via, credential:{kind, from:"auth"}}`.**
   `via:"flattened"` (mcp/openapi/graphql) → build a flattened `AddXPlatformInput` from the
   surface's `connection` template. `via:"descriptor"` (http/cli) → an opaque descriptor
   that **also needs `starterTools` merged** (the connection template omits `tools`, so it
   is NOT a valid stored connection alone).

2. **Connect branches by the user's chosen auth MODE (the mode wins over the recipe's
   default kind).** A surface declares `auth: AppAuth[]` (GitHub openapi =
   `[{mode:"oauth2",providerId:"github"}, {mode:"token"}]`). The dialog lets the user pick
   a mode among the surface's `auth[]`:
   - **oauth2 mode** → deep-link to `/credentials` (see the scope decision above). NOT an
     inline write in 30.11.
   - **token / byo mode** → a **bearer** credential via `addCredential`, secret pasted by
     the user. **`planConnect` maps token/byo → `credential.kind:"bearer"` +
     `auth:{scheme:"bearer"}` on the platform input, IGNORING the recipe's `credential.kind`
     (which is often `oauth2`).** The recipe's `credential.kind` is only the *default* when a
     surface offers a single mode. (ce-feasibility Finding 3.)

3. **Verify state is COSMETIC in the serving path — a store-then-verify wrong guess is a
   genuine false-green.** `createProfileProxy` filters sources **only** on `s.enabled`
   (`proxy.ts:140`); `resolve-provider.ts` injects the token without reading
   `lastVerifyResult`; `mcp/server` serves whatever the handlers return. An `auth-failed`
   credential is **fully servable** — its tools appear in `tools/list` and its (wrong) token
   is sent on `tools/call`. So the roadmap's hard rule demands the wrong guess **not
   persist**, not merely show a red badge. → **§3 architecture.**

4. **The catalog ships surfaces for GitHub ONLY, and no `starterTools` anywhere.** GitHub's
   mcp/openapi/graphql are `via:"flattened"`; its cli/http are `via:"descriptor"` +
   `verify:none` + **zero starter tools**. GitHub openapi/graphql ALSO offer `{mode:"token"}`
   — a PAT used as bearer, verifiable via `verifyOperationId: "users/get-authenticated"`.
   **That is the QA proof path** (§6): a real GitHub PAT, real `api.github.com`, and a
   deliberately-wrong `baseUrl` that must fail verify and persist nothing.

**HARD CONSTRAINTS:**
- **This WRITES credentials** — lead reviewer **junction-credential-security**. The
  plaintext secret exists only in a `*.server.ts` handler, never crosses the client
  boundary, never enters a return/log/toast. The recipe + `connection` template stay
  server-side; the client sees only a metadata-only `ConnectPlanPreview`.
- Web is **server-only core** (`docs/rules/web.md`): all core/recipe/secret access in
  `*.server.ts`/`createServerFn` handlers; `pnpm web:leakcheck` (empty) + `pnpm
  web:css-tokens`. Design-token discipline; semantic HTML; component tests.
- **`pnpm verify` is THE gate**; web work also needs `pnpm dup` (jscpd bit inc 30) before
  push. **QA is agent-browser against the REAL running server** + a real GitHub round-trip
  (§6) — a green build is NOT proof (the "green but blind" class, bit 8×).
- Do **not** weaken inc 28.9's manual `addCredential`/`testCredential` behavior. The new
  gate is a **catalog-connect wrapper** that verifies **before** it decides to write.

### The validated write path
- **Platform assembly (no core `addPlatform`):** `@junction/platform-orchestration`
  `addMcpPlatform`/`addOpenApiPlatform`/`addGraphQlPlatform`/`addCliPlatform`/`addHttpPlatform`.
  **⚠️ Return shapes differ** (ce-feasibility Finding 2): only `addMcpPlatform` →
  `ResultAsync<Platform,…>` (`mcp.ts:31`); `addOpenApiPlatform` → `ResultAsync<{platform,
  toolCount, cacheFile},…>` (`openapi.ts:81`); graphql/http/cli similarly return wrapper
  objects. Unwrap `.platform` (as `addByKind` does, `platform-mutations.server.ts:427`).
- **⚠️ `addOpenApiPlatform` does NETWORK I/O + a DISK cache write during assembly**
  (`openapi.ts:96` fetch/parse spec; `:163` `writeFile` to `<home>/openapi/<id>.json` via

  that cache (`build-provider.ts:118`). So openapi verify-before-commit needs the cache
  present. **The cache file is a benign, idempotent artifact** (keyed by platform id,
  overwritten on retry) — it is NOT a "connection" and its presence after a failed verify is
  acceptable (§3 makes this explicit; the atomicity guarantee is about the DB `platforms`/
  `credentials` rows, not the spec cache).
- **Credential add (non-oauth2):** core `addCredential(input, platform, store, credentialsRepo)`
  (`add-credential.ts:61`) — takes a **`Platform` object** (NOT a persisted-row lookup):
  `store.set` then `repos.credentials.create` (`:76`). `AddCredentialInput = {platformId,
  account, kind (non-oauth2), secret}`. Rejects `oauth2` (`:84`); validates via
  `isKindAccepted(platform, kind)` (`kind-compat.ts:133`; `bearer` always accepted). Web wrapper
  `mutateAddCredential` (`mutations.server.ts:94`) — verify runs **after** store, never blocks.
- **Verify (pure, no persisted row):** `verifyCredential(platform, secret, paths, opts?)`
  (`verify-credential.ts:211`) → `ResultAsync<VerifyOutcome, never>`; `VerifyOutcome =
  {status:"ok"} | {status:"auth-failed"} | {status:"unreachable", detail} |
  {status:"not-verifiable", reason}`. Takes a `Platform` object + plaintext. OpenAPI verifies
  only if `verifyOperationId` set; http/cli/custom → `not-verifiable`. ⚠️ `null`/`""` secret →

- **`platforms.upsert` is create-or-REPLACE by id** (`repositories/platforms.ts:78`,

### 2d. Starter tools (§4.7) — scope
Descriptor surfaces (http/cli) need `starterTools` merged to build a valid connection, and

## 3. The architecture — verify-before-commit + collision guard

**One rule:** *catalog-guessed connection details must prove themselves against the real
upstream before junction commits a connection the guess produced, and a connect must never
silently overwrite an existing platform.*

### 3a. Verify-before-commit (token/verifiable)
Build the `Platform` object from the recipe via the orchestration `addXPlatform` (unwrap
`.platform`), then `verifyCredential(platform, secret, paths)` **BEFORE any DB write**; only on
`ok` do `repos.platforms.upsert(platform)` + `addCredential`. On `auth-failed`/`unreachable` →
**no DB write** (no platform row, no credential). Verify against the in-memory `Platform` object;
`addCredential` takes that object directly, so nothing in the credential write needs a persisted
platform first.

**Spec-cache caveat (ce-feasibility Finding 2):** for openapi, `addXPlatform` fetches the spec
and writes `<home>/openapi/<id>.json` during assembly (and openapi verify READS it). That cache
file may exist after a failed verify — **this is acceptable and intended**: it's an idempotent
artifact keyed by id, not a connection. The atomicity guarantee is **DB-row-level** (no
`platforms`/`credentials` row on a wrong guess). §6.3's assertion is a DB query, and the method
states the cache-file exception so ce-correctness tests the right invariant.

### 3b. not-verifiable → explicit-confirm-then-write
http/cli/openapi-without-verifyOperationId → `verifyCredential` returns `not-verifiable`; there
is nothing to dry-run, so the **user's explicit confirm IS the gate**. upsert + `addCredential`,
badge `Configured`. Never a fake green.

### 3c. Platform-id collision guard (ce-spec-flow C2/C3 — data-integrity)
Before any `upsert`, resolve the platform id and **look it up** (`repos.platforms.get(id)`):
- **exists, DIFFERENT kind** (e.g. `github` openapi exists, now connecting graphql which also
  resolves to `github`) → **refuse** with a typed `ConnectError{kind:"platform-kind-conflict",
  existingKind, requestedKind}`, surfaced in the dialog ("A GitHub REST platform already uses
  this id; connecting GraphQL would overwrite it. (Multi-surface-per-app is coming in a later
  step.)"). Do NOT overwrite. *(This also explains why GitHub's mcp/openapi/graphql all sharing
  `{app}` is a real limitation until 30.12's `{app}-{kind}` groupability lands — record it.)*
- **exists, SAME kind** → this is the multi-account case, which 30.11 defers (§2e): since the
  Connect button only shows when `connections.length === 0`, a same-kind existing platform means
  a connection already exists → the button isn't shown, so this branch is defensive. If reached,
  **add the credential to the EXISTING platform WITHOUT re-upserting its connection config**
  (preserves any user edits from inc-26 `/platforms`) — do not clobber.
- **absent** → normal path: verify (3a) → upsert + addCredential.

### 3d. Why this is ONE validated path
Every branch still terminates in the same `upsert`/`addCredential` calls the manual flow uses.
The catalog wrapper adds a **pre-write verify gate + collision guard on machine-guessed values**;
it does not modify `addCredential` or 28.9's manual mutation. Correctness/security over speed,
root-cause over symptom.

## 4. Build plan — a wave (blocking core/shared slice, then the web leaf)

### Slice A (blocking) — recipe interpreter + verify-gated executor (`touches: core/apps, source-runtime`)

1. **`packages/core/src/apps/build-recipe.ts` (NEW, pure, no I/O):**
   - `resolvePlatformId(template, appId): string` — substitute `{app}` (accept `{kind}` for

     **Precedence (ce-feasibility Finding 3): the user's `authMode` selects the credential kind**
     — `token`/`byo` → `bearer` + `auth:{scheme:"bearer"}` on the platform input, ignoring the
     recipe's `credential.kind`; the recipe's kind is only the default when the surface offers a
     single mode. `oauth2` → `{path:"oauth-handoff", providerId}` (no inline write). Produces a
     discriminated `ConnectPlan`: `{path:"credential", platformInput (AddXPlatformInput |
     descriptor with merged starterTools), credentialKind:"bearer"|…, platformId, kind,
     verifiable}` or `{path:"oauth-handoff", providerId}`. Reject with a typed `RecipeError`
     (descriptor surface with no `starterTools`; an auth mode the surface doesn't offer).
   - A **metadata-only `ConnectPlanPreview`** projection (id, kind, human connection summary,
     authModes, verifiable) for the client — NEVER the secret, never the raw recipe.
   - Tests: every GitHub surface × offered auth mode → expected plan; token → bearer (NOT the
     recipe's oauth2); descriptor-without-starters → `RecipeError`; oauth2 → `oauth-handoff`;
     `{app}` substitution.
2. **`packages/source-runtime/src/connect-from-catalog.ts` (NEW) — verify-gated executor** for the
   token path:
   - `verifyThenAdd({platformInput, kind, credentialKind, account, secret, paths, repos, store}):
     ResultAsync<ConnectResult, ConnectError>`:
     (a) **collision guard (§3c):** `repos.platforms.get(platformId)` — different-kind →
     `err(platform-kind-conflict)`; same-kind → add-credential-only path (no re-upsert);
     (b) assemble the `Platform` via the orchestration `addXPlatform` (unwrap `.platform`);
     (c) `verifyCredential(platform, secret, paths)` — `ok` → `upsert` + `addCredential`;
     `auth-failed`/`unreachable` → return the outcome, **zero DB writes**;
     `not-verifiable` → the executor persists (it's the confirm-gated branch — web passes a flag,
     OR web calls a separate `confirmThenAdd` that skips verify; keep it explicit, not implicit).
   - Reuses `verifyCredential`, orchestration `addXPlatform`, core `addCredential`. Typed errors;
     no bare throws. **Boundary:** source-runtime lib — may import core + libs, NOT apps, NOT
     `mcp-server` (`source-runtime-not-mcp-server`). Tests with a stub upstream: `ok` → both
     writes; `auth-failed` → assert `repos.platforms.upsert` NOT called + `addCredential` NOT
     called; different-kind existing → conflict error, no write.
3. **GitHub http starter tools** (§2d): `github/tools/http.tools.json` + regen
   `catalog.generated.ts` (codegen; CI git-diff-checks). Doc the proof-exception in the file.

Gate A: `pnpm verify` (incl. catalog codegen diff + depcruise). Commit-to-lock.

## 8. Risks / watch-outs
- **Orphan platform row on verify-fail** — #1 trap. Verify against the in-memory `Platform` BEFORE
  any `upsert`. The openapi spec-cache file is a benign exception (§3a); assert DB rows, not files.
- **Platform-id collision** (ce-spec-flow C2/C3) — GitHub's mcp/openapi/graphql all resolve to
  `{app}`; a second connect must REFUSE (different kind), never overwrite. §3c.
- **token-mode maps to bearer, not the recipe's oauth2 kind** (ce-feasibility Finding 3) — the auth
  mode wins.
- **`not-verifiable` honesty** — badge `Configured`, "couldn't verify"; never a fake green.
- **Empty-secret anonymous verify** (inc 28.9 hole) — Confirm disabled on empty + server rejects
  empty pre-verify; always pass real plaintext.
- **oauth2 is a deep-link hand-off, NOT an inline write** (scope decision, §0) — do not attempt
  `startConnect` from the recipe (it needs BYO client creds the recipe lacks).
- **`cli` `credentialEnvVar`** — `GH_PAT` not `GH_TOKEN`.
- **Return-shape** — orchestration adders return `{platform, …}` (except mcp); unwrap `.platform`.
- **Green-but-blind** — the proof is the real GitHub round-trip + DB-unchanged-on-wrong-guess, NOT
  the gates. **`data.server.ts` binary byte** — `grep -a`.
- **Commit discipline** — `--no-verify` skips the biome-write hook → `pnpm biome check --write
  <files>` before push; long timeout for the pre-push full-verify (~135s). Guard against in-flight
  git from concurrent sessions.
