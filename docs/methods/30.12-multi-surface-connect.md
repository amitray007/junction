## §0 — Load-bearing facts (proven, not assumed)

These were **empirically confirmed against the real built artifact** (`node --input-type=module`
against `packages/core/dist/index.js`) before this file was written — not read off docs:

1. **The collision is real and wider than "3 surfaces".** GitHub's `openapi`, `graphql`, `mcp`,
   AND `cli` surfaces ALL use `build.platformIdTemplate: "{app}"` → all four resolve to
   platformId **`github`**. Only `http` uses `"{app}-http"` → `github-http` (distinct). So today,
   connecting a 2nd *flattened* surface hits `checkCollision`'s different-kind branch
   (**`packages/source-runtime/src/connect-from-catalog.ts:113`** — this file lives in
   `@junction/source-runtime`, NOT core; every `connect-from-catalog.ts` citation in this doc means
   the source-runtime one) → **refuse, zero writes**. (Verified: openapi/graphql/mcp/cli → `github`;
   http → `github-http`.)

2. **The grouping bug is ALREADY SHIPPED and latent, not just future.** `appIdForConnection`
   (`core/apps/group.ts:54`) attributes by oauthProviderId → exact-id → alias → displayName → `"other"`.
   A platform id `github-mcp` (or the already-live `github-http`) matches NONE of these →
   falls to **`"other"`** and **VANISHES from `/app/github`**. Verified empirically:
   `appIdForConnection({platformId:"github-http"})` → **`"other"`** TODAY. So even 30.11's shipped
   `http` surface, if connected, would already vanish from its app page. This is a bug 30.12 fixes,
   not merely a forward concern.

3. **`brave-search` (the only hyphenated app id) proves the precedence.** `appIdForConnection("brave-search")`
   → `"brave-search"` (exact-id match, step 2) — must resolve BEFORE any suffix-strip. Verified.

4. **No app id ends in a build-kind suffix.** Audited all 45 `listApps()` ids: none ends in
   `-mcp`/`-openapi`/`-graphql`/`-http`/`-cli`. So the `<appId>-<kind>` scheme is
   **unambiguously reversible** over the real catalog — the suffix-strip rule has zero false
   positives today. (A catalog-invariant test will keep it that way — see Slice A.)

5. **The multi-account backend is DONE; only the UI defers it.** `checkCollision`'s SAME-kind
   branch (`connect-from-catalog.ts:92-122, 240-247`) already handles "platform exists, same
   kind → add credential only, no re-upsert." The verify-before-commit gate
   (`verifyThenWrite`, `connect-from-catalog.ts:255-290`) already applies. 30.11's Connect button
   is gated on `connections.length === 0` (`app.$id.tsx:671, 709`) — a pure UI omission.

6. **Duplicate `{platformId, account}` silently double-inserts.** The `credentials` table
   (`core/db/schema.ts:26-43`) has **no** unique index on `(platform_id, profile_name)` (only
   `sourceRefs`/`apiKeys` do). `addCredential` (`core/credentials/add-credential.ts:61`) mints a
   fresh ULID PK and inserts with no dup check. Two "default" accounts on one platform → two
   indistinguishable rows. **This is a latent correctness gap in CLI + `/credentials` + the new
   add-account path.** Verified: no `uniqueIndex` on credentials; the dogfood db has 0 credentials
   (so any guard we add can't retroactively conflict).

7. **The `duplicate-account` error does NOT auto-surface as per-outcome UI copy — it must be WIRED
   (both doc-reviewers flagged this).** `mapConnectError` (`web/server/connect.server.ts:180-184`)
   maps ONLY `platform-kind-conflict`; every other `ConnectError` (incl. the `credential-failed`
   wrapper around `duplicate-account`) → generic **"Failed to connect this surface"**. And three
   `CredentialError` consumers handle the variant differently: `cli/format.ts:155`
   `formatCredentialError` is a **defaultless exhaustive switch** → adding the variant to
   `CredentialError` FAILS the build here (self-catching, good); but `cli/commands/credential.ts:860-876`
   `reportCredentialOpError` and `web/server/mutations.server.ts:135-144` `mutateAddCredential` are
   **if-chain fallthroughs** → they COMPILE clean and misbehave silently (empty CLI error / leaked
   raw enum token) unless explicitly updated. A grep-for-`switch` finds only `format.ts`. Verified:
   GitHub's openapi/graphql/mcp surfaces offer `auth: [oauth2, token]` (multi-mode), so the add-account
   dialog SHOWS the auth-mode Select — the multi-mode path is the REAL GitHub path, not an edge.

## §1 — What / why (the increment in one paragraph)

Surfaces should **accumulate**, not collide. Connecting a 2nd surface for an app (e.g. GitHub's
`mcp` after its `openapi`) must produce a distinct platform (`github-mcp` vs `github-openapi`) that
still **groups back under `/app/github`**. This is the `<appId>-<kind>` groupability rule from
`30.5-app-lifecycle.md` §425-439 — but here in service of **accumulation** (re-framing "Change
method" as *add a surface*, not swap). Two additional gaps close in the same increment: (a) the
already-shipped grouping bug where `<appId>-<kind>` platforms vanish to "other", and (b) the
30.11-deferred **multi-account-via-Connect** UI gap — surface an "Add account" affordance on an
already-connected surface (backend already supports it). A latent duplicate-account correctness
gap is closed at the root (`addCredential` typed guard) — **user decision 2026-07-07: app-level
guard, no DB migration** (the DB unique-index is deferred to futures as a dedup-then-constrain
hardening).

**Proof-of-done (the whole increment is done when):**
- Connect GitHub's `graphql` surface, THEN its `mcp` surface → both persist as distinct platforms
  (`github-graphql`, `github-mcp`) and BOTH appear under `/app/github` (neither in "Other").
- `appIdForConnection({platformId:"github-mcp", kind:"mcp"})` returns `"github"` (not "other");
  `appIdForConnection({platformId:"brave-search"})` still returns `"brave-search"` (exact-id wins).
- On an already-connected surface, an "Add account" affordance appears; adding a 2nd account with a
  DISTINCT label persists a 2nd credential on the SAME platform (no re-upsert). A 2nd account with
  a wrong token → verify fails → **nothing persists** (verify-before-commit inherited).
- Adding a 2nd account with a DUPLICATE label → typed `duplicate-account` error, **nothing written**
  (proven at the `addCredential` layer AND surfaced as a per-outcome inline UI error).
- `pnpm verify` green; depcruise green; catalog regenerated + git-diff-clean.

## §2 — Interfaces / architecture (what changes, precisely)

### Slice A — core (BLOCKING; lands + `pnpm verify` + committed-to-lock FIRST)
`touches: [core]`. No web. No migration.

**A1. `appIdForConnection` suffix-strip rule** — `packages/core/src/apps/group.ts`.
Insert a NEW step **4** (between alias match at :83 and displayName match at :85):

> **Step 4 (NEW):** if `platformId` ends in `-<kind>` where `kind ∈ {mcp, openapi, graphql, http, cli}`
> (a **closed set of the 5 build-recipe kinds** — NOT `custom`), strip exactly that trailing suffix
> once and retry the exact-id match (step 2's logic) against the stripped base. Match → return that
> app id. No recursion, no second strip, do NOT fall through to alias/displayName on the stripped base.

Precedence rationale (load-bearing): exact-id (2) and alias (3) are authoritative zero-ambiguity
matches — they MUST win first so a real id like `brave-search` is never mis-stripped. The strip
goes BEFORE displayName (5) because a structurally-generated `<appId>-<kind>` id is a stronger
signal than a displayName coincidence.

- Define a module-level `const BUILD_KIND_SUFFIXES = ["mcp","openapi","graphql","http","cli"] as const`
  (do NOT derive from `PlatformKind` — that includes `custom`, which must not strip).
- Anchor to the trailing suffix only (`-${kind}` at end of string), strip once.

**A2. GitHub catalog templates** — `packages/core/src/apps/catalog/github/catalog.json`.
Change the FOUR bare `"{app}"` templates (openapi, graphql, mcp, cli) → `"{app}-{kind}"`.
Also normalize http's `"{app}-http"` → `"{app}-{kind}"` (resolves identically to `github-http` —
equivalent; makes "every catalog surface's platformId is `<appId>-<kind>`" a clean uniform invariant).
`resolvePlatformId` (`build-recipe.ts:165`) already substitutes `{kind}` — no code change there.
**Regenerate** `catalog.generated.ts` (`node packages/core/scripts/gen-catalog.mjs` or the repo's
gen script — check `package.json`; CI git-diff-checks it, so it MUST be regenerated and committed).

**A3. `addCredential` duplicate-account guard** — `packages/core/src/credentials/add-credential.ts`.
Add a NEW typed error variant `duplicate-account` to `CredentialError` and check for an existing
`{platformId, account}` BEFORE the store write + insert. Return `Err({kind:"duplicate-account",
platformId, account})` if a credential with the same `platformId` + `profileName` already exists.
- Use `credentialsRepo.forPlatform(platformId)` (confirmed accessor, `credentials.ts:77`) and check
  `existing.some(c => c.profileName === accountToCompare)`. Do the check AFTER input validation,
  BEFORE touching the secret/store (mirrors the early-exit discipline — bad input never touches the store).
- **TRIM/CASE CONTRACT (doc-review pinned — A3 and B2 MUST agree):** `addCredential` does NOT trim
  `account` today (`add-credential.ts:120` passes `input.account` straight to `CredentialSchema`);
  the web caller does `account.trim() || "default"` at the edge (`app.$id.tsx:523`). So: the guard
  compares the **exact stored `profileName`** against the **exact `input.account` as `addCredential`
  will store it** — i.e. do NOT add a trim inside `addCredential` that the write itself doesn't apply
  (that would let a trailing-space label pass the guard then store a different string). The match is
  **case-SENSITIVE by deliberate decision** (`profileName` is `z.string().min(1)`, case-preserving —
  the store has NO case rule, so "Work" and "work" are legitimately distinct accounts; do NOT
  lowercase-compare). B2 (the client guard) must mirror EXACTLY: compare the trimmed submit value
  (`account.trim() || "default"` — what the edge sends) against the stored labels, case-sensitive.
- **NAME the three CredentialError consumer sites (grep-for-switch finds only the first):**
  1. `cli/format.ts:155` `formatCredentialError` — defaultless exhaustive `switch` → adding the
     variant FAILS the build here until a case is added (self-catching; add a friendly message).
  2. `cli/commands/credential.ts:860-876` `reportCredentialOpError` — **if-chain fallthrough**,
     compiles clean; add `duplicate-account` to its branch list so `credential add` prints the real
     message (else it misroutes to `reportDbError` → empty output).
  3. `web/server/mutations.server.ts:135-144` `mutateAddCredential` — **if-chain fallthrough** that
     `return e.kind`s (leaks the raw token); add a friendly `duplicate-account` message (the
     `/credentials` add path is protected by the same guard, so its UX must be honest too).
  Message shape: `"an account named \"<account>\" is already connected to this platform"`.
- This protects ALL edges (CLI `credential add`, web `/credentials`, the new add-account path) at
  the root. **No DB migration** (per user decision) — record the DB `uniqueIndex` hardening in
  `docs/futures/gotchas.md` with the dedup-then-constrain trigger.
- **Confirmed shapes (verified in-repo, don't guess):** the accessor is
  `credentialsRepo.forPlatform(platformId): ResultAsync<Credential[], DbError>`
  (`core/repositories/credentials.ts:77`). The new error variant slots into `CredentialError`
  (`core/errors/index.ts:20-26`) as `| { kind: "duplicate-account"; platformId: string; account: string }`.
  Every exhaustive `CredentialError` switch/formatter (grep `kind: "kind-incompatible"` /
  `kind: "invalid-input"` handlers across cli/web/core) must gain the new case — NEVER add a
  non-exhaustive `default` to silence tsc (documented trap: phantom exhaustiveness errors are stale
  `.tsbuildinfo` → fix with `pnpm build`, never a `default`/`as never`).
- **Catalog regen (A2) is a real gate:** run `pnpm --filter @junction/core gen:catalog` (script
  `gen:catalog` → `node scripts/gen-catalog.mjs`); CI's `catalog:check` git-diff-checks
  `catalog.generated.ts`, so it MUST be regenerated + committed or CI fails.

**A4. NO change to `intersectSurfaces`** (`core/apps/surface-connections.ts`). It matches
