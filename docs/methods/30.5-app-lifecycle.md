## 3. Slice 1 — Test-Connection auto-refresh fix

### What & why
`testCredential` must, for an oauth2 credential, refresh the access token **before** verifying
— identically to how the runtime resolve path already refreshes on use — so a refreshable
credential reports its true status, not the status of its stale token.

### Approach (recommended — hold loosely)
1. **Surface the full credential row** (not just `secretRef` + `oauthProviderId`) from
   `loadPlatformForCredential`, so `testCredential` has `credential.kind`, `credential.id`,
   and `credential.oauthMeta` — the inputs `refreshIfExpired` needs. (Or fetch it again; a
   single extra `repos.credentials.get` is fine, but threading the already-fetched row is
   cleaner.)
2. In `testCredential`, **before** the current `store.get`/verify block, branch on
   `credential.kind === "oauth2"` and mirror `resolve-provider.ts` L126–172:
   ```ts
   // oauth2: refresh-ahead so Test reports the TRUE status, not the stale token's.
   const refreshResult = await refreshIfExpiredSingleFlight(credential.id, () =>
     refreshIfExpired({ credential, store, repos, refreshFn: oauthRefreshFn, now: Date.now() }),
   )
   ```
   Map the outcome to `TestCredentialResult`:
   - `needs-reauth` → this is an HONEST **auth-failed** for Test (the credential genuinely
     needs reconnect — surface it as auth-failed, matching what the runtime shows the agent).
     Consider a `detail` like "needs reconnect". (Decide: auth-failed vs a distinct
     not-verifiable — recommend **auth-failed**, it's the truthful "you can't use this now".)
   - `refresh-failed` → **auth-failed** (can't get a trustworthy token right now), or
     **unreachable** if the failure is transient/network — recommend **auth-failed** to match
     resolve-provider's mapping (L152–163). Hold loosely; whichever, it must NOT be a false
     "ok".
   - success → use the refreshed `accessToken`; if `null` (lost secret) → the existing
     `STORED_SECRET_MISSING_DETAIL` unreachable path (do NOT verify with a null/`""` token).
3. For the refreshed token, call `verifyCredential(platform, refreshedToken, getPaths(),
   { oauthProviderId })` exactly as today. Non-oauth2 credentials keep the current plain
   `store.get` path **unchanged**.
4. `setVerifyState` persistence stays as-is (the refresh mutating the stored token is a
   separate, already-atomic write owned by `refreshIfExpired`).

### DRY note (architecture — decide at build)
`resolve-provider.ts` and `testCredential` now both do "get the current oauth token for a
credential, refreshing if due, single-flighted." That's **two** call sites. If a clean
shared helper falls out (e.g. `getCurrentOAuthToken(credential, store, repos)` in
source-runtime returning `Result<{ accessToken }, RefreshError>`), extract it — BUT the two
callers map the error to different shapes (`UpstreamError` vs `TestCredentialResult`), so the
helper should return the raw `RefreshError` and let each caller map. Rule-of-three is arguably
not yet hit (2 sites); **prefer the smallest correct duplication over a premature abstraction**
unless the builder sees the extraction is genuinely cleaner. If duplicated, keep the two blocks
obviously parallel and comment the cross-reference. **Watch jscpd** — two near-identical refresh
blocks may trip `pnpm dup`; if so, that's the signal to extract (the honest fix, per inc-30).

### Boundary / security
- All secret handling stays server-side (`mutations.server.ts` is server-only). The refreshed
  token is NEVER returned to the client — `testCredential` returns only `{ status, detail? }`.
- The refresh may rotate the stored token (a real DB write) as a side effect of Test — this
  is correct and desirable (it's the same rotation the runtime does), but **call it out in the
  PR** so the security reviewer sees Test now has a write side-effect.

### Concurrency (state this in the PR so the security reviewer doesn't flag a phantom race)
The single-flight key is **`credential.id`**, IDENTICAL to resolve-provider's
(`refreshIfExpiredSingleFlight(credential.id, …)`). So a Test firing while an agent call
resolves the SAME credential **coalesces** into one refresh — no double-rotation, no
lost-update race. The "Test rotates the stored token" write side-effect is real and correct
(it's the same rotation the runtime does), just single-flighted with the runtime path.

## 4. Slice 2 — Per-app icons

### Decision — v2: **full-color logos via `@thesvg/icons`** (user feedback 2026-07-04)
The first cut used `simple-icons` (monochrome, `currentColor`). **The user rejected it** — the
gray glyphs read washed-out / fake, especially the multi-color marks (Google, Slack, Microsoft
rendered as flat gray). New decision (user + research): **real full-color brand logos** that
still adapt to both themes, via **`@thesvg/icons`** (npm, MIT code / per-icon CC0-1.0 logos,
4400+ brands, tree-shakeable, raw SVG strings — offline, no CDN). Verified mechanically: it
ships the authentic multi-color marks, has **28/28 of our catalog** (incl. slack + microsoft,
which simple-icons had *removed*), and carries per-icon `variants: { default, mono, light,
dark, wordmark }`.

**The both-themes strategy (per-category — this is the crux):**
- **Category A — full-color, legible on both themes → render `variants.default` as-is.**
  ~most marks: google, slack, microsoft, gitlab, figma, discord, stripe, linear, spotify,
  dropbox, notion, etc. Colored logos read fine on dark or light; do nothing special.
- **Category B — pure black/white marks → light/dark variant swap** (user chose this over a
  currentColor mono). github, vercel, railway ship `variants.light` + `variants.dark`; emit
  BOTH inner-SVGs and let CSS show one per `data-theme` (`[data-theme="dark"] .brand-dark`
  visible, `.brand-light` hidden, and inverse). Two elements, one visible, no flash, no JS.
- **Notion special case:** its `default` is a 2-tone mark that may vanish on one theme; it has
  a `mono` variant → render `mono` with `fill="currentColor"` (auto-adapts, faithful — Notion's
  real mark is essentially monochrome). Verify Notion specifically on BOTH themes at QA.

**Icons are pinned via a checked-in codegen (user chose this):** a build-time script extracts
ONLY the ~28 used `{ viewBox, variants{ default/light/dark/mono as inner-SVG markup } }` from
`@thesvg/icons` into a **committed `brand-icons.generated.ts`**. `@thesvg/icons` stays a
**devDependency** (its 90 MB never enters the runtime tree; ~28 icons ≈ tens of KB bundled).
This **fails loudly at codegen** if a slug disappears upstream (trademark takedown — the
simple-icons Slack/Microsoft precedent), converting the top risk into a caught-at-build event.

### Approach
1. **Core (pure data):** `iconSlug?: string` on `AppDefinition` (already added in v1 — keep).
   It's the `@thesvg/icons` slug (e.g. `"github"`), NOT a Platform.id. Re-verify each slug
   resolves in the installed `@thesvg/icons` (the API is `import x from "@thesvg/icons/<slug>"`
   → `{ slug, title, hex, svg, variants, license }`). Populate for apps with a real logo; leave
   undefined → letter-tile fallback. No migration (catalog is code). Expand coverage now that
   slack/microsoft/box/adyen/etc. ARE available (retire most letter-tile fallbacks).
2. **Codegen → `brand-icons.generated.ts`:** a build-time node script (checked into
   `packages/web/scripts/` or similar, run via a `package.json` script + wired into the build
   BEFORE `vite build`) that reads the catalog's `iconSlug` set, imports each from
   `@thesvg/icons/<slug>`, and emits a typed committed module:
   `{ [slug]: { viewBox, category: "color"|"themed"|"mono", default?, light?, dark?, mono? } }`
   where each variant value is the **inner SVG markup** (strip the outer `<svg>` wrapper; keep
   its `viewBox`). Category is derived: has light&dark → `"themed"`; notion → `"mono"`; else
   `"color"`. **Fail loud:** throw (non-zero exit) if a catalog `iconSlug` has no `@thesvg/icons`
   module or the chosen variant is empty — never emit a blank. Commit the generated file (it's
   the pinned snapshot); re-run codegen only on a deliberate icon-set change.
3. **`BrandIcon` component (rewrite):** render from the generated map by category:
   - `"color"` → one `<svg viewBox={vb} aria-hidden>` with the raw inner markup.
   - `"themed"` → TWO `<svg>` (light + dark), CSS-swapped on `data-theme` (add the two utility
     classes to the design-system CSS; must be reduced-motion-agnostic, pure display toggle).
   - `"mono"` → one `<svg fill="currentColor" aria-hidden>` with the mono inner markup.
   - unknown/undefined slug → `<LetterTile>` (keep from v1). Glyph is DECORATIVE (name is
     always visible beside it) → **`aria-hidden="true"`** on all of them (the v1 a11y fix — keep).
   - **Rendering the raw inner markup WITHOUT `dangerouslySetInnerHTML`:** the codegen must emit
     the inner SVG as **parsed React elements** (a build-time SVG-string→JSX transform in the
     codegen, so `brand-icons.generated.ts` exports real JSX/element trees, not strings) — keeps
     the no-`dangerouslySetInnerHTML` / no-CSP-change posture. If a safe parse is impractical,
     the fallback is a vetted static-string `dangerouslySetInnerHTML` on BUILD-TIME-TRUSTED,
     committed markup only (never runtime data) — but prefer the parsed-elements route; flag if
     you must fall back.
4. **Render sites (unchanged from v1 — keep):** `PageHeader` `leading?` slot; `/app/:id` header
   + `/app` cards pass `<BrandIcon slug={app.iconSlug} displayName={app.displayName} />`.
5. **License/notice (update the wording):** replace the simple-icons notice with:
   *"Brand logos provided by @thesvg/icons (github.com/glincker/thesvg, MIT), each mark under
   its upstream license (mostly CC0-1.0). All product names, logos, and brands are property of
   their respective owners and are used for identification only under nominative fair use; no
   affiliation or endorsement is implied."* (README "Third-party notices" — the location v1
   established; keep it there.)

**Trademark posture (honest):** full-color marks lean a bit harder on nominative fair use than
a monochrome silhouette (the official colored mark is more strongly "the brand"). Mitigations:
identification-only use in an integrations list, marks unmodified, brand's own colors preserved,
no endorsement implied + the notice above. Residual risk = a brand requesting removal (a
takedown, not a suit); the codegen pin + letter-tile fallback contain it.

## 5. Slice 3 — Change method (swap a connection's vertical)

### What & why
From `/app/:id`, a connection's ⋯ menu gains **"Change method"** — swap the vertical junction
uses to reach that service (e.g. GitHub-via-REST → GitHub-via-MCP). Because a REST connection
and an MCP connection are **different Platform rows + different Credentials**, this is NOT an
in-place edit. It must be **additive and reconnect-first** so a failed/abandoned swap leaves
the original connection fully intact.

### ⚠️ The redirect-continuity constraint (load-bearing — a doc review caught this)
The connect step is a **browser OAuth redirect**: the app navigates OFF to the provider and
returns via `/oauth/callback`, which today **always** `throw redirect({ to:"/credentials",
search:{connect} })` (`oauth-connect.functions.ts` L110–120) and the `PendingAuth.intent`
union (`pending-auth.server.ts` L28) has only `create`/`update` arms. **So there is no way,
as written, for the "confirm to remove old" step to appear after the round-trip** — the user
would land on `/credentials?connect=ok` with BOTH connections and no confirm, silently
violating the user's explicit-confirm decision. The swap intent MUST survive the redirect
server-side. **The builder cannot discover this from the happy-path narration — it is
specified here:**

- **Add a third `PendingAuth.intent` arm:** `{ mode:"swap-create"; platformId; account;
  supersedes:{ oldPlatformId; oldCredentialId } }`. `persistOAuthTokens` treats it exactly
  like `create` (stands up the new credential on the new platform).
- **`completeOAuthCallback`, on a successful `swap-create`**, records a **pending-teardown
  marker** (keyed by the new credentialId, holding `supersedes`) and redirects to
  **`/app/:id?swap=confirm&old=<oldCredentialId>`** (NOT `/credentials`). Add a `swap` case
  to the callback search so the loader can read it.
- **Teardown is a SEPARATE, user-driven mutation** — NEVER an auto-delete inside the callback.
  The `/app/:id` loader reads `?swap=confirm`, renders the explicit confirm dialog; its
  confirm button calls the existing `mutateRemoveCredential(old)` + `deletePlatformFn(old)`.
- On error/abandon the callback redirects with `connect=error*` and NO teardown marker — the
  old connection is untouched (nothing removed) and the new half is the user's to retry/remove.

### The flow (additive, reconnect-first, explicit-confirm teardown)
1. User picks "Change method" on an existing connection → picks the **new kind** (from the
   app's `supportedKinds` minus the current one).
2. **Stand up the NEW connection first:**
   - Create the new-kind **Platform** row. **Platform `id` is a user-supplied PK** — reusing
     the app id (e.g. `github`) COLLIDES with the existing connection's platform. Derive a
     new non-colliding id: **`<appId>-<newKind>`** (e.g. `github-mcp`). See the
     **groupability requirement** below — this id choice is load-bearing.
   - **Connect the new Credential** via the connect flow that **reuses the OLD credential's
     stored client creds** (see NEW HELPER) with a **`swap-create` pending intent**.
   - **Verify the callback / new credential is `ok`** BEFORE touching the old one (the callback
     completing is the verify; optionally a `verifyCredential` too).
3. **Only after the new connection verifies OK** — the callback lands on
   `/app/:id?swap=confirm&old=<id>` and the page shows an **explicit confirm step** ("Remove
   the old <old-kind> connection?"). On confirm: `removeCredential(old)` then
   `deletePlatform(old)` (both RESTRICT-FK guarded). **If the old is in-use → see the
   in-use policy below** (do NOT leave the user with a bare `in-use` error + both connections).
   If the user declines, BOTH connections remain — no stranding, no forced destruction.
4. On ANY failure/abandonment before step 3's confirm, the OLD connection is untouched.

### ⚠️ Groupability requirement (a doc review caught this — critical for non-OAuth swaps)
The new connection MUST group under the **same** `/app/:id` it was launched from.
`appIdForConnection` (`core/apps/group.ts` L54) attributes by: authoritative
`oauthMeta.providerId` → exact `platform.id === app.id` → aliases → displayName → `"other"`.
- **OAuth new kind:** fine — the new credential carries the app's `oauthProviderId`, so it
  groups by L68 regardless of the `<appId>-<newKind>` platform id.
- **Non-OAuth new kind (e.g. MCP with token/none auth):** there is NO `oauthProviderId`
  anchor. A platform id of `github-mcp` matches neither `github` by id nor by alias → the new
  connection falls through to **`"other"` and VANISHES from `/app/github`** — the exact page
  the swap started on. **Fix:** for a non-OAuth new kind, the new platform id (or an alias on
  it) MUST resolve to the app — add `<appId>-<newKind>` as an **alias** on the AppDefinition,
  OR give the platform the app id in a form `appIdForConnection` matches. **Proof-of-done:
  post-swap, `appIdForConnection(newConnection)` returns the app, NOT `"other"` — assert this
  explicitly for a non-OAuth new kind.** (This is why the non-OAuth case, below, is more than
  a footnote.)

### ⚠️ In-use old-credential policy (a doc review caught this — DECISION, see §5b)
If the old credential is referenced by a profile `source_ref`, `removeCredential` returns
**`in-use`** and teardown fails — leaving BOTH connections + a raw error + the profile still
pointing at the OLD vertical. This is NOT a benign "RESTRICT did its job" — in a swap the user
was just told "we set up the new one, now remove the old." The policy is a **user decision
recorded in §5b**; whichever is chosen, the proof-of-done must cover it (never a bare `in-use`
error with both connections stranded).

### The NEW helper (the core of this slice)
A named helper that starts an OAuth connect for a **NEW platform target** while **reusing an
existing credential's stored client creds cross-vertical**. Shape (recommend; hold loosely):
```ts
startConnectReusingClientCreds({
  sourceCredentialId,   // the OLD credential whose clientIdRef/clientSecretRef to reuse
  providerId,           // the new vertical's oauth provider (may equal the old)
  scopes,
  newPlatformId,        // the NEW platform row this connection stands up
  account,
}) → { authorizeUrl }
```
- It resolves `clientIdRef`/`clientSecretRef` from the source credential's `oauthMeta` (the
  SAME reuse logic `startReconnect` already has at oauth-connect.server.ts L139–158 — extract
  that resolution into a shared internal `resolveClientCreds(credential)` rather than copy it,
  so the two paths can't drift), then drives `buildAuthorizeUrl` + `putPending` with a
  **create-intent targeting the NEW platform** (`intent: { mode:"create", platformId:
  newPlatformId, account }`).
- **It must NOT** mutate or read the old credential's *access/refresh tokens* — only the
  BYO client_id/client_secret refs. Never carry a token into the new flow.

### Security invariants (this slice gets a dedicated security pass)
- **No stranding:** the old platform+credential are removed ONLY after the new one verifies OK
  AND the user confirms. A crash/abandon anywhere before that leaves the original live.
- **No client-cred leak:** the reused client_id/client_secret stay refs in the store; resolved
  server-side only; NEVER returned to the client, logged, or put in a URL/argv (they go into
  the pending-auth server-singleton like the existing connect flow, not the browser).
- **No orphaned refs:** if the new connect fails after minting new store entries, clean them up
  (mirror `persistOAuthTokens`'s store-first→delete-old atomicity). The old refs are never
  touched until teardown.
- **Non-oauth verticals:** if the new kind is token/none (not oauth2), there's no client-cred
  reuse to do — it's a plain platform-add + credential-add; the helper is oauth2-specific.
  Scope the first cut to the verticals the reuse matters for; be explicit about what's covered.

### §5b — In-use old-credential policy — DECIDED: **auto-repoint old→new** (user, 2026-07-04)
As part of confirm-teardown, **repoint each referencing `source_ref`** from the old
credentialId to the new one, so the profile follows the vertical change — THEN remove the old
credential + platform (which now succeed, no longer in-use). Requirements + the honest caveat:
- **New core op needed:** `sourceRefs.repoint(oldCredentialId, newCredentialId, newPlatformId)`
  (does NOT exist today) — atomically updates every `source_ref` pointing at the old
  credential/platform to the new one. Repoint the platform reference too (the new vertical is a
  new platform row). This is a `core` op (the swap composes it in web).
- **⚠️ toolFilter caveat (surface honestly, do NOT silently drop):** a profile route's
  `toolFilter` was written against the OLD vertical's tool *namespace* (e.g. REST operationIds);
  the NEW vertical (e.g. MCP) exposes DIFFERENT tool names. A blindly-carried filter may match
  nothing (or the wrong tools). **Recommended handling:** on repoint, **warn the user which
  routes had a toolFilter** and that the swap **clears/resets** those filters to "all tools"
  (safe default — over-expose nothing silently; the user re-narrows on the new vertical), OR
  carries them with an explicit "review your tool access on the new method" nudge. Decide the
  exact behavior at build; the invariant is **no silent filter that now means something
  different than the user intended.** Record the choice in `revisit-when.md`.
- **Ordering:** repoint FIRST (inside the confirm-teardown transaction/sequence), then
  `removeCredential(old)` + `deletePlatform(old)` — which now pass RESTRICT because nothing
  references the old anymore. If repoint fails, abort teardown (old stays live, both connections
  remain — no stranding).
