| **Concurrent-boot-during-rotation availability note** | Master-key rotation becomes long enough (very large vault) that a concurrent `junction` boot failing during a rotation is a real UX wrinkle | inc 32.3 `rotateMasterKey`/`recoverInterruptedRekey` take the shared `.credentials.lock` with NO `retries` on the ROTATION side (deliberately unchanged by 32.13), so a second process booting mid-rotation gets `ELOCKED` → `rotate-failed` → the store won't open until rotation finishes. | **Store-split-brain: a keyring↔file backend flip silently produces null reads** | An operator's `JUNCTION_STORE` env or keyring availability changes between runs (e.g. a machine migration, a keyring daemon becoming unavailable, or a deliberate `JUNCTION_STORE=file` override introduced mid-lifecycle) | Neither backend persists which backend was ACTIVE when a given secret was written — `resolveStore`/`selectStore` re-derives the backend fresh on every boot from the current environment + keyring probe, with no stored "this vault's secrets live in backend X" marker. If a secret was written under keyring and a later boot resolves to the file backend (or vice versa), every `store.get` for that secretRef returns `Ok(null)` — indistinguishable from "never set" — rather than a typed cross-backend error. **Symptom:** a credential row exists in the DB with a valid secretRef, but the tool call silently gets a null secret (surfaces downstream as an auth failure with no clear cause). Forward path: a persisted active-backend marker (e.g. `<home>/.store-backend`) written on first successful store init, checked on every subsequent boot — a mismatch surfaces a typed `store-backend-mismatch` CredentialError instead of a silent null. Deferred — no report of this actually occurring; multi-env/backend-flip is not today's common case. (raised inc 32.13 audit) |
